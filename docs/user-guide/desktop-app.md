# OHL-Design, the line application

**OHL-Design** (the program `ohl-design`, formerly `ols-cad`), the line application of OpenOHL — sag-tension, clearances, line layout — opens a line file or a project and shows it in dockable views that share the selection and the weather case.

Your settings, the files opened recently and the plugins installed for you stay where they were before the project was renamed: the application's data folder still carries the name "OLS CAD" (the structure application's: "OLS Structure"), so nothing is lost. The old program name `ols-cad` still starts `ohl-design` for a while (it says so on the terminal).

```bash
cargo run --release -p ohl-app -- examples/synthetic-line/synthetic-line.ohl.json \
    --terrain examples/synthetic-line/synthetic-survey.csv \
    --weather examples/synthetic-line/weather-cases.ohlwc

cargo run --release -p ohl-app -- project.ohl          # with the project's point cloud
cargo run --release -p ohl-app                         # the start page: File › New project, Open
```

On macOS, double-click **Start OHL-Design.command** at the top of the source tree: it builds and starts the app on its start page (new project, open, the files opened recently). New to OpenOHL? The start page offers **New project from the starter template…** and **Open the example (copy)…**, and **Help › Start from scratch** will open the tutorial, which is not written yet (the entry is greyed out until it is; see [Starting from nothing](#starting-from-nothing)). Libraries given on the command line apply to the file given there only; files opened from the File menu use their own (a project's are kept in it).

| Option | Meaning |
|---|---|
| `--library` | Wire library (file or directory); default: the `*.ohlw` files next to the model, else `libraries/cables`. |
| `--structures` | Pylon files; default: the `Structures/` folder next to the model. |
| `--insulators` | Insulator library directory. |
| `--weather` | Weather cases (`.ohlwc`); default: still air at 15 °C. All cases are solved. |
| `--terrain` | Survey points for the ground. |
| `--pointcloud` | Point cloud in a project (`FILE.ohl` or `FILE.ohl#name`) or a COPC file (`FILE.copc.laz`, streamed by node, see [Point budget](#point-budget)); default: the project's own. |
| `--points` | About how many LiDAR points are shown (default 2 000 000). Points of **every class** of the whole cloud are shown, ground classes and noise included: a class of up to 20 000 points whole, the larger classes thinned alike to the budget. The ground surface is built from all points of the ground classes (lowest per 1 m cell) in the corridor. |
| `--corridor` | Half width of the corridor around the spans the ground surface is built in (default 60 m). |
| `--user` | The user editing the project (default: the login name), see [Editing](#editing). |
| `--rules` | Clearance rules (`.ohlr`) for the Clearances tab; default: the only `.ohlr` of the project (next to a line file). |
| `--load-cases` | Load cases (`.ohllc`) for the structure loads; default: the project's own, else the first `.ohllc` next to the file. |
| `--class-scheme` | LiDAR class scheme (`.ohlc`: class names, roles, colours) used instead of the point cloud's own. |
| `--controls` | Navigation scheme: `orbit` or `minecraft` (default: the one used last). |
| `--screenshot FILE.png` (`--focus ID`, `--distance M`) | Load, render the 3D view to an image and exit (with `--focus`, looking at that structure's first wire point, from `--distance`, default 250 m). |

**Weather cases are solved when needed:** opening a model solves only the weather case shown first. Another case is solved in the background the first time it is shown (Display weather cases, a section's own display case); the status bar says which are being solved. A check or a script that needs a case solves it first. Edits re-solve the cases already solved; the others are solved from the line as it is when they are first shown. The Model page lists the cases not solved yet.

**Opening a menu stops what was going on**, as Escape would: a captured mouse is freed, a wire being strung or an alignment being laid out is given up, so the menu's commands work on the first click.

Right of the menus, the **quick bar**: the commands chosen for it (default **Undo, Redo, Save all**, Fit views, **Check wire clearances** — Undo, Redo and Save in the same place as in OHL-Structure); under the menus, the line's name and the selection. **⚙** (or View › Customize the quick bar) adds any command of the menus — commands, library editors, tools — removes and orders them; the bar is remembered (a bar customized before keeps its commands).

**Pages** work like browser tabs: each has a tab with a close button; drag a tab to rearrange, or out of the window to make a floating, resizable window with its own row of tabs (drop more pages on it). A **right-click on a tab**: **Dock on the left** (with Model, Clearances, Next steps), **Dock on the right (with Properties)**, **Float in a window of its own**. Closed pages come back from View. Library editors and tables open together in a floating window — dock them like any page.

**Tool windows as panels.** The windows a tool or a command opens and closes again — the editor windows (structure, string, section, jumper, span point…), **New pylon from a template**, **Place on alignment points**, **Replace structure**'s mapping, the **Vertical** and **Radial clearances** windows, **Display weather cases** — come up floating where they always did. **📌 Dock as a panel** (top right of the window) makes one a tab of the main window (with Properties, on the right): drag it anywhere there or out again, or slide it aside behind another page; **⬈ Float** makes it a window again. It still closes when its tool is done (Apply, Cancel, the tool finished), and its tab with it; closing its tab closes the tool (as Cancel). Docked once, it comes up docked the next time (in this session).

## Starting from nothing

**The starter template.** File › New project… › **Starter template (for learning)** (or the start page's **New project from the starter template…**) makes a project in local coordinates (metres) whose libraries hold a small set of examples — every value invented or typical, clearly marked, nothing for design: a wire library (ACSR conductors), two structure types of level 1 (a suspension and a strain tower, built from the pylon template `delta-1c`), insulator assemblies, weather cases, load cases and a clearance rule file; beside the project, the pylon templates `delta-1c` and `barrel-2c` (in its `Pylon templates` folder) and `starter-survey.csv`, survey points of invented ground to import with Terrain › Terrain surfaces (TIN). It has **no route, alignment, structure or wire**: the planned tutorial (**Help › Start from scratch**, greyed out until it is written) will walk through making them — the route, the alignment, the first structures, the strings on them, the cable and the stringing, the jumpers; until then, [A new line, step by step](getting-started.md#a-new-line-step-by-step) and **Next steps** show the way. The files are `examples/starter/` of the source tree (its README lists them); the tutorial will use the same.

**Next steps** (a page, View › Next steps, Help › Next steps; in front when a line has no structure yet) lists what the line still needs, in the order of the work, worked out from the project each time it is drawn: a route, an alignment, the ground, structure types, structures on the line, strings on them, cables, wires strung, jumpers (where a line needs them), weather cases, load cases, clearance rules. Each step says what the project has, or how it is done, and is a link to where it is done — the first steps window, a tool held (New alignment, Add structure, Add string, String wire, Add jumper), Terrain surfaces, New pylon from a template, Place on alignment points, a library page, Vertical clearances. The next step is in bold.

When the first point of a new alignment is typed or clicked on an empty line, the views go to it; the first structures of an empty line fit the plan and the 3D view.

## Views

- **3D** — ground (shaded), LiDAR points coloured by class role (vegetation green, buildings red, water blue, wires yellow…), structures, insulator strings, wires in their phase colours (bundles as their subconductors, `bundle_spacing` apart — one section, solved and selected as one — held at every clamp by a yoke: a bar for two, a triangle for three, a polygon for more; the back and ahead spans and the jumpers end on its corners), alignments. Navigation: see [Controls](#controls). Height exaggeration in the Model panel.
- **Plan** — alignments, wires and structures from above, north up, with a scale bar. Drag, scroll at the pointer, double-click to centre. With View › Sheet preview ticked, each sheet of the drawing export is shown as its band along the alignment (the line width each side), its match lines and its number (see [Sheet preview](drawings.md#sheet-preview)).
- **Profile** — per route, or **All alignments, in order** (the first, then the second… each starting where the one before ends, its name at the start): ground along the centreline, structures and wires by station: the spans between the structures following each other along the alignment, and those to a structure of the route **away from the alignment** (more than 5 m beside it and not tied to one of its points — a connection or termination beside the line, on the route because it gives it): projected at its station, fainter, its distance from the alignment written after its name (*C1 (80 m right)*); the spans along the alignment go on past it. The same holds for the drawings, and the line angles and spans ahead (stationing, structure loads) are taken along the alignment's structures, without those away. **line width ±** (m, default 40 m) is the drawings' line width — one setting with **Line width** in File › Export › Drawings…, kept with the project line (see [Drawings](drawings.md#line-width)) — and shows what lies that far left and right of the alignment: the ground at both edges (thin, darker), the survey points of the ground surface (dots), the LiDAR points loaded (in their class colours; classes hidden in Terrain › LiDAR classes shown are left out) and the 3D lines and points of the drawings (DXF, in their colours; flat 2D drawings have no heights and are left out; hidden drawings are not drawn), projected on the profile; a structure away from the alignment is shown only within it, and wires out to one beyond it are cut at it (as in the drawings); heights fit the visible stretch, or keep the ratio chosen in View › Profile aspect ratio (written at the top left). Scroll zooms at the pointer (at a fixed ratio the height under the pointer stays under it), drag moves (also up and down at a fixed ratio), double-click shows the whole route. The profile view is **continuous** along the route: it never breaks into sheets. Sheets — their format, scales and breaks — belong to the drawing exports (**File › Export › Drawings…**, see [Drawings](drawings.md#sheets)). The **Sheets** menu above the view (also View › Sheet preview; a menu of ticks, it stays open) shows the export's sheets over the profile and the plan when ticked (off by default): match lines at the sheet ends, sheet numbers in a strip along the bottom, the export's warnings above the view, laid out by the export itself with the settings of the export window and following them as they change (see [Sheet preview](drawings.md#sheet-preview)).
- **Properties** — the selected structure (position, type, attachments, spans through it) or span (cable, circuit, electrical system and voltage, bundle, horizontal and maximum tension, sag and lowest point in every weather case). Links select related objects.
- **Model** — layers, sections or jumpers that failed to solve, by weather case (click one: that case is shown, the object selected and the views brought to it), what was loaded and how long it took (folded: **Loaded**; library files of the project are named by their name, not by their working copy's temporary path).
- **Next steps** — see [Starting from nothing](#starting-from-nothing).
- **Sections not solved** are drawn in each weather case they fail in, in the 3D and plan views, as a **dashed red** line where they were: their last solved shape in that case (an edit made them fail: the shape before it), else their shape in another weather case, else the straight chords between their wire points. Hovering one in the plan says why; a click on any drawn copy selects the span (all copies highlighted), and its properties say why it did not solve in that case and where the drawn shape comes from.
- **Structures by usage** — on the Structure loads page (Checks › Compute structure loads), view Usage, **Colour structures by usage** colours the structures in the 3D and plan views by their usage (green, orange from 90 %, red over 100 %; a neutral grey-blue for those **not checked** because a section or jumper at them did not solve; dark grey without capacity), with a legend at the bottom right; see [Structure usage](loads.md#structure-usage-capacity-checks).
- **Clearances** — clearance violations of the shown weather case (see [Clearances](#clearances)).
- **Properties** of the other kinds: a wire point with a set (its strings — top, wire point, length, weight, insulator, compression —, spans and jumpers there), an alignment point (position, tied structure), a LiDAR point (position, class and roles).

## Level of detail

The 3D view draws the large layers — terrain, LiDAR points, structures, wires, other weather cases, other project lines, DXF drawings — in **chunks**: the 256 m tiles of the project grid (the grid of the project file's spatial index). Every frame, each chunk in view is drawn at a **level of detail** from its distance to the eye; chunks outside the view or beyond the layer's render distance are not drawn, and those far beyond (1.5 × the render distance) leave the GPU. Missing chunks are built nearest first, a few milliseconds per frame, so the view never freezes: until a chunk's level is built, a level already built is drawn. An edit rebuilds the layers of the line, not the terrain and the LiDAR points.

**View › Advanced › Level of detail** (a page) is the table of these settings, a row per layer, every value typed in, remembered with the window layout:

| Layer | Level 0 | Level 1 (default from) | Level 2 (default from) | Render distance |
|---|---|---|---|---|
| Terrain | every TIN triangle | the surface on an 8 m grid (1.5 km) | a 32 m grid (5 km) | 30 km |
| LiDAR points held in memory | the share of the survey chosen in Survey data display options (default 25 %; 100 %: every point) | 25 % of that (500 m) | 5 % of that (1.5 km) | 3 km |
| Structures | members (types at levels 2 and 3) or stick drawing, arms, strings | mast, arms and strings (2 km) | the mast line (8 km) | 50 km |
| Member and pole solids (one value: **solids up to**, under the table) | members with a library profile and poles at levels 2 and 3 as solids of their real outline, in the chunks closer than this | | | 400 m |
| Wires, other cases, project lines | every point; bundles as subconductors with their yokes; clamps, marker balls and other bodies to their shape, bare span points' marks, jumpers' support clamps | 16 points per span, one line per bundle; line codes' dashes 4 × longer; bodies as dots, clamps and marks left out (1.5 km) | 5 points per span; dashes 16 × longer; spreads, spacers and arrows left out (6 km) | 50 km |
| Drawings (DXF) | every vertex and point | lines simplified to 0.5 m, lines and points smaller left out (1 km) | simplified to 2 m (4 km) | 10 km |

Sections not solved in a weather case are drawn dashed red at every level, their dashes longer farther like the line codes'. Labels: in 3D, the section labels, sags and the labels of points and strings are written within the label distance of the eye (Display options, default 1.5 km); the **structures' names** (when ticked) at any distance — they are placed first, the other labels give way to them, and where names would overlap the nearest is written. In the plan the structures' names are always written, at every zoom, first in line order where they would overlap (the selected one always); sags and section labels only for the spans in view long enough on the screen. The plan draws what is in view only, a far view's points crowded into one pixel once; the profile draws one survey point per pixel and keeps what it drew while the view does not move. The 3D image is drawn again only when the camera or what is on the GPU changes (a frame for another panel shows the same image).

**Structures at levels 2 and 3** ([detail levels](structure-library.md#detail-levels)) are drawn with their **members**, placed as the line places their type — at the structure's position, turned to its orientation, on its extension (the extension's piece and leg extensions included), raised by its height adjustment — the same lines the profile and the drawings use. A type that names a separate `.ohlfe` model is drawn with that model's members. Close by — in the chunks nearer than the **solids distance** — a member whose section is in the [section library](section-library.md) with a profile is also drawn as a **solid** of the profile's outline about the member's axis, turned as the structure check turns it (`reference`, `roll`, an angle's `orientation`); fillets are left out, round shapes are drawn as 16-sided polygons and tubes as closed. Members with a `[[section]]` table of their own (no profile) or without a section stay lines. From afar the members are lines, farther the mast line (the table above).

The **solids distance** is its own setting, **Member and pole solids up to … m** under the Level of detail table (default 400 m; 0: no solids; at most the structures' render distance), apart from the structures' level 0: the lines follow the Structures row, the solids this distance. It is a chunk's distance (its nearest point to the eye), so the solids of a whole 256 m chunk come and go together. The default comes from measurements (Development › Performance, *Member and pole solids*): a lattice tower with every member a solid is some 3 500 triangles; on a line of such towers 400 m apart the frame time stayed under half a millisecond from 0 to 2 km, so the distance is set by what can be seen — beyond a few hundred metres a member is under a pixel and a pole one or two, the lines drawn over them give the shape — while 400 m keeps the structure in front and its neighbour solid. Raise it for close-up work along a line; 0 draws no solids.

**Poles at levels 2 and 3** (a `[pole]` outline with diameters at two heights at least, or a named `.ohlp` file) are drawn with their **outline** within the solids distance: a solid of the pole's real outline by height — round (16 sides) or a regular polygon (across flats as given, a flat facing the structure's −y), tapered linearly between the given heights — from the ground line to its top (the part in the ground left out), hollow with its wall (inner faces and the rings at its ends) or solid; a `[pole]` at level 2 without a wall is drawn solid. It stands where the line places the type: the structure's position, orientation and height adjustment, raised by its extension (the lowest diameter held down to the ground). Its lines (the mast line and arms of its stick drawing) are drawn as before at every level, so from afar a pole is its mast line. Clicking inside the pole on the screen (where no line is near) selects its structure. Poles at level 1 are drawn as before. Structures at level 1 are drawn as before (their stick drawing, or a mast and arms). The geometry is made once per type and extension when the libraries are read and only moved for each structure, so a line of many structures of one type costs little more than the lines it draws. Drawing only: the checks use the structures as they are.

Clicking a member selects its structure. When the structure screen of the Structure types page shows that structure's type, the member is selected there too. Structures are drawn once, not per weather case, so every member drawn can be clicked.

The last column of the table shows what was drawn in the last frame: the chunks at each level, of how many, and how many are still loading. On a 25 km line seen from 1.5 km, 5 million terrain triangles became 280 000 drawn, 1.5 million LiDAR points 24 000, and 190 000 wire segments 14 000; every chunk builds in under 2 ms.

### Point budget

A survey stored in the project — or a COPC file opened as the point cloud (`--pointcloud survey.copc.laz`) — is not drawn by the table's levels but **streamed by node under a point budget**. Its nodes are, for a stored survey, each 256 m square at four levels (about 1/64, 1/16, 1/4 of its points, then every point: the [levels of detail](project.md#levels-of-detail) stored in the project), and for a COPC file its octree. Every frame:

1. the nodes in view and within the LiDAR row's render distance are taken, the coarsest first;
2. a node whose points lie farther apart on the screen than the **error** allowed (default 1.5 px) is refined — its finer level, or its octree children — the one with the largest error (the nearest) first;
3. until the next node would exceed the **point budget** (default 5 million points; the share of Survey data display options thins every node further and counts in the budget).

The missing nodes are read on background threads (half the cores, at most four), each with its own reader of the project file, in that order; the queue is replaced every frame, so it never lags behind the camera. Until a node is read, a coarser (or finer) level of its square already read is drawn. Nodes read stay on the GPU while they are in view; beyond 1.5 × the budget the least recently used are dropped. Classes of up to 20 000 points are read whole at every level (wires, towers); hidden classes are not read.

**View › Advanced › Level of detail** sets the budget (0.1–200 million points) and the error (0.1–50 px), remembered per user, and shows what the last frame did: nodes drawn of how many, points drawn and wanted, whether the budget was reached, what is on the GPU and still loading.

Measured on an Apple M1 Max (synthetic survey of 25 million points on 2.5 km × 2.5 km, 1600 × 1000 view, error 0.3 px so that the budget limits the view; `point_budget_frame_times`, release build, GPU time included):

| Budget | Points drawn | Read in | Frame while turning (median / slowest) |
|---|---|---|---|
| 2 million | 1.97 million | 0.07 s | 7.7 ms / 9.8 ms |
| 5 million | 4.97 million | 0.13 s | 16.5 ms / 19 ms |
| 10 million | 9.9 million | 0.23 s | 32 ms / 35 ms |

The frame time grows with the points drawn (about 3.3 ns a point on this GPU), not with the size of the survey: what a frame touches is bounded by the budget and the nodes in view (choosing them takes microseconds). For 60 frames a second, keep the budget near 5 million on such a machine. A survey of 10⁹ points on disk has more nodes (a few thousand for a 100 km corridor), read the same way: the index of its blocks once when the view opens (about 0.4 s per 10⁵ blocks; 10⁹ points are some 10⁵), then each node as it comes in view. Not measured at that size here (only synthetic data is used for performance, and the largest run is 25 million points). The synthetic grids also compress to almost nothing: real surveys decode several times slower than the 25–45 million points a second measured above, so expect nodes to arrive a few times slower — the frame rate does not depend on it.

The level of detail changes what is **drawn** only: calculations, checks, the profile, the plan and picking always use the full model.

## Weather cases shown

**Display weather cases** (View menu) chooses how the wires are shown:

- **The same weather cases for every section**: tick one or several (the list scrolls in a box of fixed height); every section is drawn in each case ticked. Display only — the Sections table's display cases are kept (not used while this is chosen).
- **Each section's display weather case (Sections table)**: every section in its own display cases; sections without one in the cases ticked above. Setting display cases in the Sections table chooses this too.
- **Wind**: from the right, from the left, or **both sides** (each case with wind solved and drawn twice; the wind from the right is the one checked). The side the wind comes from is a display choice, not part of the weather case.

Wires are drawn with their jumpers, yokes and **insulator strings, to their clamp as solved in each case** (swung by the wind, moved with the temperature). Labels (section labels, sags, structure labels) are written once per section, in its first case: the other cases show their wires only. In 3D, labels are written only within a distance of the eye — 1500 m unless set otherwise in either Display options menu ("3D labels within … m of the eye") — and are not even built beyond it, so a long line stays fluid. Every copy drawn can be clicked — anything that moves with the weather case — a span, jumper, string, wire point, span point or spacer — in any of the cases shown (either wind side) — and selects the object (Edit opens it as usual). The selection is highlighted in every case it is drawn in, the copy clicked the strongest, and its properties mark the case of that copy (▶, coloured) in their list of weather cases. The first case is the one checked for clearances. These choices are yours, remembered with the project on this computer. In the properties, a span's or jumper's results in every weather case are listed in a box of fixed height, scrolled.

The model's **weather case file** is remembered with the project (`--weather`, or **Use for the model** in the Weather cases library editor, Criteria menu): opened again without `--weather`, the project uses the file it used last.

## Project lines

A project holds several designs of the line — the **main line** and, for example, the **phases** of the project — each edited on its own. You work on one at a time (Versions › Project lines…, or the Versions menu): your edits and Undo apply to it; others are shown next to it in their colour. A new line is a copy that then lives its own life; **Bring in changes** updates it from another line, and a phase goes back into the main line through a review. On a server each user chooses their own line. Everything is described in [Project lines and phases](project-lines.md).

## Saving

Every edit is stored in the project file as it is made (the operation log), so nothing is lost when the app stops. **⌘S** (Ctrl+S on Windows and Linux, or File › Save all) writes the project file through, saves the library pages with changes that read (the model reads them again) and says which table changes are still pending (Apply makes them). **⌘Z** / **Shift+⌘Z** (Ctrl+Z / Shift+Ctrl+Z) undo and redo, outside text fields.

## Loads for structures

What the line sends to its placed structures (**Open in OHL-Structure…** on a placed
structure starts the [structure application](structure-app.md#started-for-a-placed-structure)
with that place's loads) is set up in three places of the **Criteria**
menu:

- **Weather cases**: the wind, ice and temperatures. Each one can be sent
  on its own.
- **Load cases** (a `.ohllc` file) or **Design code** (a plugin writes the
  load cases): a weather case with a wire condition and factors on the
  vertical, transverse and longitudinal loads. They add factors and
  combinations on top of the weather cases.
- **Loads for structures**: a tick menu (it stays open while ticking)
  with two lists. **Load cases**: those sent (all by default, also those
  added later; **all** / **none**). **Weather cases (all factors 1)**:
  those sent on their own, each as a case `weather: <name>` with every
  factor 1 and the wires as strung (none by default; **none**). A ticked
  case no longer in the line stays listed, marked, to be unticked. Each
  tick is one edit of the project line's settings (undoable, the
  `structure_loads` row), so every project line keeps its own choice.

The structure application gets the load cases sent, then the weather
cases sent, each marked with its source. A line with no load case and no
weather case ticked sends nothing: the structure application says so and
suggests ticking weather cases here.

## Tools: hotbar and inventory

As in Minecraft, the bottom of the 3D view holds a **hotbar** (it goes with the 3D view when another page is in front; the inventory shows it to arrange it) of nine tool slots. Choosing a slot — **1–9**, a click on it, or the **wheel** while the mouse is captured in first person, one slot per wheel notch (a trackpad steps at a steady pace; Ctrl + wheel stays the speed) — only *holds* its tool; a **right-click** on an object uses it (in first person, on what is under the crosshair) — or a left-click, with the option [**Tools act on left-click**](#tools-act-on-left-click). The tools by theme — **General**: Select, Edit, Delete, Go to structure (G); **Alignments**: New alignment, Add alignment point, Edit alignment; **Structures**: Add structure, Move structure (M), Replace structure, Add string; **Wires**: String wire, Add jumper, Add on span (see [Editing](#editing) and [Routes and alignments](#routes-and-alignments)). A new user's hotbar holds Select, Move structure, Delete, Go to structure, Edit, Add structure, Add string, String wire and **New alignment**; the others wait in the inventory. Holding a tool that is not in the hotbar (from the Tools menu, a key, a link of Next steps) puts it into an empty slot — the active one if it is empty — else into the last slot: never over the first slot (Select) nor over the tool held. A left click selects (a right-click with the option on); a right-*drag* still pans. A window opened by a tool (Move, an editor, the confirmation of a deletion, Go to) frees a captured mouse and opens at the crosshair (or at the mouse outside first person), also when it replaces a window already open for another object; it can be dragged anywhere, also partly off the screen. **E** opens the **inventory** with every tool, grouped by these themes (the **Tools** menu lists them in the same order, a line between themes) (**E** or **Escape** closes it); only while it is open can the hotbar be arranged: drag a tool onto a slot, drag slots to swap them, drag a slot back to the inventory (or right-click the slot) to empty it. The arrangement is remembered. New tools are added to the inventory as they come. Each tool has its icon (the drawings of `assets/icons/tools/`) in its slot, in the inventory, in the **Tools** menu and on the quick bar; in the menus it takes the text colour of the theme (light or dark). The window and the start page show the OpenOHL mark and OHL-Design's icon; **Help › About** shows the mark with the version.

## Clearances

There are three ways to check clearances, each for its own targets: **Ground clearances** (Checks menu) — **Vertical clearances…** and **Radial clearances…**, to the ground and the LiDAR points, with rules typed in each window ([below](#vertical-and-radial-clearances)); **Wire clearances** — between the wires of this line and with exclusion zones, by the rules of a rule file (its rules to other lines are not run here: the results list them as skipped, for `ohl line --other-line`), run by **Check wire clearances** (Checks › Wire clearances, or the quick bar), results on the **Clearances** page. The menu and the page say which is which.

The **Clearances** tab checks the shown weather case with a rule file (`.ohlr`, the format of `ohl line --rules`; see [Clearance rules](terrain.md#clearance-rules-ohlr)): the wires against the ground surface, against the LiDAR points of the rules' classes, and against the line's other wires, with the requirements by voltage of each section's electrical system. Rule files are listed from `--rules FILE` and the project's `.ohlr` files (next to a line file); the one given or the only one found is chosen at start. Without one, the page says so and offers **Add a rule file…** (a `.ohlr` file chosen on the computer, checked, kept in the project — `examples/starter/rules` has one with invented values to learn with) and the two ground clearance windows.

**Edit rules** (under the rule file chosen) edits its rules in place: per rule its name, its target, and its **vertical** and **radial** clearance (ticked: given), each set as [one distance, a table by voltage or a base plus an amount per kV](#distances-by-voltage). **Add rule** adds a rule to the ground, between the wires of this line or to other lines (rules to LiDAR classes come from the clearance windows or a preset); **Remove** asks first. A change is written when the mouse is released and every rule is complete ("not written yet: …" says what is missing); comments, the fields the editor does not show and the order of the file stay as they are. For a project's rule file each change is **one command: Undo takes it back** (the editor follows the file). **Load preset…** opens **Rule presets**: the presets of clearance rules of the design-code plugins turned on in the plugin manager (their optional `rule-presets` export; read with the parameter file chosen in Criteria › Design code, if any — see [Design codes](design-codes.md#rule-presets)). Choose one to see its description, each rule with its distances and their values at the project's voltages, and its weather cases; then **Merge into FILE** (a rule of the same name replaced in place, the others added) or **Replace the rules of FILE** (the preset's rules alone, its `[wind]` and `[check]` too). Either is one write of the rule file (one command); the preset's weather cases missing from the model are added to the model's weather case file, as for the windows' presets.

#### Distances by voltage

Wherever a rule's distance is set — the Clearances tab's rule editor, the clearance windows' rules and their **Add a rule** — a chooser gives three forms, so one rule covers every voltage:

- **one distance** — the same for every voltage (typed beside it);
- **table by voltage** — rows "up to kV: distance", the first row whose voltage the wire's nominal voltage does not exceed (earthed wires: 0 kV). In its menu (it stays open while you work): **Add row** (up to the project's next voltage above the last row, else 100 kV above it), **Remove**, **Sort**; voltages must increase and distances be above 0;
- **base + per kV** — base + per kV · (U − from kV) above "from", else the base.

The menu shows the distance at **the project's voltages** (each system's nominal voltage, and 0 kV for earthed wires). A warning says what is missing — a distance not set, voltages not increasing, a project voltage above a table's last row ("the project has 380 kV above the last row (245 kV): add a row"); such a rule is not written, and a check refuses a table that does not reach a wire's voltage. For wire rules the voltage is the pair's (`pair_voltage`, see [Clearance rules](terrain.md#clearances-by-voltage)). The forms are written as the rule file's `"7 m"`, `{ by_voltage = [[up to kV, "distance"], …] }` and `{ base = …, per_kv = …, above_kv = … }`, read back exactly.

Checks run **on demand**: **Check wire clearances** (Checks › Wire clearances, or the quick bar) or **Check now** in the tab; tick "after every edit" to check again after each edit and change of weather case. The check runs in the background. LiDAR points are read again from the project's point cloud each time, only those of the rules' classes in a corridor around the spans, so nothing more is kept in memory: on the 25 km line with 18.8 million such points a check takes a few seconds. The list shows each violation, worst first: wire (span or jumper, and the other wire for wire rules), rule, vertical or radial clearance against the requirement, the LiDAR class, how many points are too close. Clicking one selects the wire and brings the views to it. The violations are drawn in red in the 3D view (a line from the wire to the point too close; layer "Clearance violations") and circled in the plan.

Rules for other lines and rules across pairs of weather cases are run by `ohl line` only; the tab says so.

The **Analyses** entries of the Checks menu open windows that compute on demand in the background, each with a results table (click a span to go to it) and CSV export — see [Galloping, blowout, vegetation and as-built wires](analyses.md): **Galloping ellipses** (a `.ohlg` parameter file and a weather case), **Vegetation** (danger trees: the point cloud's vegetation classes near the wires of the cases ticked — blown left and right, along the swing arc, with unbalanced ice — growth, trees falling in about their root ball, isoclearance lines; drawn on the layers *Vegetation: grow-in*, *Vegetation: danger trees* and *Isoclearance lines*), **As-built wires** (catenaries fitted to the wire points, the temperature at the survey).

### Vertical and radial clearances

**Checks › Ground clearances** opens two windows: **Vertical clearances…** and **Radial clearances…**. Each checks the spans and jumpers against its own list of rules. The window can be closed at any time; closing it stops a check that runs.

**The zone.**

- **Vertical**: an area of points straight under (and over) the wire: **width on each side** (default 1 m) across the line, in plan, and **depth** (default 0.2 m) along it. The clearance is the shortest vertical distance between the wire and a point of the area: a point is compared with the wire's lowest point within the depth around it (its highest for a point above the wire — rare, but measured the same way). Bundles: the lowest (highest) subconductor. A rule may have **its own width** (the rules' **width m** column: click the window's width, shown in brackets, to give the rule its own; × goes back to the window's).
- **Radial**: the direct 3D distance from the wire, to each subconductor of a bundle.
- **Ignore LiDAR points farther than … m from the wires** (both windows; unticked: as far as the rules reach): only the points within that distance of the wires are read and compared.

**What is solved.** **Circuits**: the circuits checked, ticked by circuit name (none ticked: every circuit). **Solved by**: each section's own calculation (the default), or every section by **finite elements** or by **ruling span** for this check (each keeps its cable condition).

**The rules.** One row per rule: a name, the **voltage** of the wires (any, or one of the line's systems; earthed wires are 0 kV), the **weather cases** (ticked; none ticked: every case), the **distance** to keep — one distance, a table by voltage or a base plus an amount per kV ([Distances by voltage](#distances-by-voltage)): with "any" voltage one rule gives each wire the distance of its voltage — the vertical window's **width** (the rule's own, or the window's), the **wires** checked (the sections' spans, the jumpers, or both — the default) and the **targets**: LiDAR classes ticked from the point cloud's classes (the class scheme's when no cloud is open), and the **ground surface**. You never type a class number. **Add rule** (a blank row), **Duplicate** and **Remove** (it asks first) edit the list.

**A window always has a rule.** Opened without rules (a new project), it starts with one: **Ground** — the ground surface, any voltage, every weather case — its **distance to set** (0 m, marked "set the distance": no value is given for you; take it from the regulation you work to). **Run** is greyed out, with the reason beside it ("Before Run: …"), while a rule's distance is not set or a rule has no target; the last rule cannot be removed (change it instead). A rule whose distance is not set is not written to the rule file. **Add a rule** (open while the first rule is still to set) asks for one rule in plain fields — its name, **what** (the ground or LiDAR classes, ticked), the **voltage**, the **distance** (in any of the three forms) and the **weather cases** — with what they mean; **Add this rule** takes it into the list, in place of the first rule while that one is untouched.

**Load preset…** lists the clearance presets of the project — given by a design-code plugin when it generates (Criteria › Design code, see [Design codes](design-codes.md#clearance-presets)): a rule file and a weather case file of the same name among the project's libraries, with rules of the window's kind. Choosing one replaces the rules listed with its rules, and takes its wind, circuits, calculation method and search distance; its weather cases missing from the model are added to the model's weather case file (the model's cases of the same name are kept). Everything can be changed afterwards — the classes, the cases, the distances — and is kept as the window's rules.

**Import… and Export…** read and write rule files (`.ohlr`, see [Clearance rules](terrain.md#clearance-rules-ohlr)). A row is written as one `[[rule]]` per target kind (classes, ground), with `voltages`, `wires`, `cases`, `vertical_band` (the width: the rule's own or the window's), `vertical_depth`, a `[wind]` table and a `[check]` table (the circuits, the method and the search distance, when set), so `ohl line --rules` reads the file too (it ignores `[wind]` and `[check]`). Importing keeps the ground and point rules with a clearance of the window's kind; a requirement by voltage stays one row with its table or formula (one row per voltage only when the rule lists `voltages`; the line's voltages a table does not reach are noted); roles become their classes; the first rule's `vertical_band` becomes the window's width, another one a rule's own. The window says what it left out (rules between wires, exclusion zones).

**Without the window.** `ohl zones --rules FILE` runs the same check from the command line on a window's rule file or a preset, with the project's point cloud and ground (see [`ohl zones`](terrain.md#vertical-and-radial-clearances-without-the-window-ohl-zones)).

**Where they are kept.** Like the Clearances tab's rule files, in the project: `<model>.vertical-clearances.ohlr` and `<model>.radial-clearances.ohlr` among its clearance rules (next to a line file). Every change is kept when the mouse is released. The Clearances tab lists these files too; **File › Export › Libraries…** writes them out (folder `rules`) for `ohl line --rules`.

**Wind.** A weather case with wind is solved with the wind from **the left and the right** (default), **the left only** or **the right only** — looking ahead along the line. Untick **Step the wind** to check only the case's own pressure. Tick it to solve every pressure from 0 up to the case's, in steps of **step Pa** (default 50 Pa, at most 200 steps per case and side). The wires at all these positions form the surface the wire sweeps as the wind rises; each span's clearance is the lowest over all of it.

**Run** solves the wind positions on all cores and checks them in the background, with progress (**Stop** ends it; the time budget is 15 minutes). LiDAR points are read again from the point cloud, only those of the rules' classes near the wires (within the search distance when one is set). The results list the spans below a rule, worst first: span, rule, required and found distance, the wind pressure and side, the target (class or ground) and how many points are too close (each counted once over all wind positions; for the ground, wire pieces at the worst position). Click a span to select it and bring the views to it. The violations are drawn in red in the 3D view (layer "Clearance violations") and circled in the plan. On the synthetic example, 121 wind positions (600 Pa in 10 Pa steps, both sides) are solved and checked in under 0.1 s.

### Structure picker

A window to choose a structure type, opened from the type button of the structure window (Add structure, Edit) and from the type cells of the Structures table. ### Colour tool

A small window to choose a colour. At the top, **Wheel** or **Sliders** (your choice is remembered):

- **Wheel**: click or drag on the wheel. Round it is the hue (red to the right, green up left, blue down left). Outwards is the saturation (grey at the centre). The slider below is the brightness.
- **Sliders**: red, green and blue (0–255), and hue (°), saturation and brightness (%).

Below, the **old** and the **new** colour side by side, and the new one as `#rrggbb` (type one there too).

A click takes a colour; a double click takes it and closes the tool. Type a name and a use and press **+ Add** to add the new colour. ⏶ ⏷ move a colour, ✏ edits its name, use and colour, 🗑 deletes it (asked first). **Defaults** adds the program's own colours (phases, wires without a phase number, electrical systems) that are missing.

name = "Phase 1"

## Routes and alignments

A line is laid out in three steps, kept as three kinds of record in the project: a **route** (a path of the line), its **alignments** (each on exactly one route, in their order along it) and the **alignment points** (PIs) of each alignment, in order. An alignment cannot exist without its route. A point is an object of its own: it may be on no alignment yet, on one, or on several — with its own place (order number) in each. Where alignments of different routes meet they share the point, so the point — and a structure tied to it — is on all their routes. Structures, sections, jumpers and what hangs on structures are put on routes **from the alignments**, nothing to keep by hand:

- a structure tied to an alignment point, or within 5 m of an alignment, is on that alignment's route;
- a structure away from every alignment (a crossing line) is on no route until you give its route(s) — in its window (Edit, or when placing it) or the Structures table's **routes** column; it is said in yellow after an edit, and in its properties;
- a section is on the routes of its structures (one running from a route into another is on both), a jumper on those of its two ends.

**A new project** starts with these steps (its first window): 1. **the route** — its name and description; 2. **its alignment** — the New alignment tool is then held.

The points are drawn in the 3D view (cyan, on the ground) and in the plan — those on no alignment too — and can be clicked (Edit › Snap, alignment points). The profile follows every change at once.

- **Terrain › Routes**: one row per route — its id (renaming: its alignments and structures follow), name, description, its alignments in order, how many structures and sections are on it. **+ Add row** makes a route; deleting one asks first and lists its alignments (they go with it; their points stay).
- **Terrain › Alignments**: one row per alignment — its id, name, **route** (a dropdown of the routes; required), its order **#** (3.5 goes between 3 and 4), how many points, description. **+ Add row** makes an alignment (without points yet); with no route yet, **+ New route… / Create the route** above the table makes one. Deleting an alignment keeps its points.
- **Terrain › Alignment points**: a row per point and alignment it is on — its **alignment** (a dropdown), its place **#** there, the point's id, E, N, z, the structure it is tied to, the other alignments it is on with its place there (**also on**), description. A point on two alignments has two rows, each with its own #; a point on none has one row without alignment. A row deleted takes its point off that alignment only (the others keep their order); the point itself is deleted with the last of its rows. (The Delete tool on a point on several alignments asks: **Delete from all** — the point goes — or **Take it off the ticked ones**, its alignments listed with their routes and ticked in a scrolling list; a point on one alignment is deleted as before.) **Alignment ▾** above shows one alignment (or the points on none).
  - **#** orders the points of an alignment (3.5 goes between 3 and 4); another alignment moves the row's point there; none takes it off that alignment (it stays).
  - **+ Add row** with an existing point's id puts that point on the alignment too (shared); a new id makes a new point.
  - Deleting a row deletes the point: it comes off **every** alignment it is on (asked first when on several), the other points keep their order.
- **New alignment** (tool) lays out an alignment point by point. Each right-click adds a point:
  - **on an alignment point:** that point, shared (a junction);
  - **on a structure:** a new point tied under it;
  - **on a survey point or LiDAR point shown** (within 12 pixels): a new point at its exact E, N and height;
  - **on nothing of these:** a window asks for the point's **E, N and height** (all required; where you clicked is offered).

  **Enter** asks for its route (one: the route worked on, or that of the points it shares, is chosen; **+ New route** makes one — with no route yet, it offers to create one), then makes it (*alignment 1*, *alignment 2*…). **Backspace** takes the last point back, **Escape** gives it up (the tool stays held).
- **Add alignment point** (tool): a right-click on a survey or LiDAR point, a structure (tied under it) or the ground opens its window — its E, N and height (given by what was clicked), and **connect it to the nearest alignment**: ticked, it goes between the two closest points of the nearest alignment; unticked (the default), it is on no alignment yet — New alignment then picks such points one after another, like the String wire tool picks strings.
- **Edit alignment** (tool) changes the course of an alignment. Right-click one of its points, then the new points (snapped as for New alignment; an existing point is shared), then:
  - **another point of the same alignment:** the points between the two are replaced by the new ones (those taken off stay, on no alignment unless on another);
  - **Enter, from its first or last point:** the new points are added there, before its first or after its last;
  - **Enter, from a point in its middle:** an alignment has two ends only, so it branches — a new alignment from that point through the new ones is offered, its route asked as for New alignment.

  **Backspace** takes the last point back, **Escape** gives it up.
- **Edit** (tool) on a point opens its window: E, N, z or *on the ground*, tied to a structure, and the alignments it is on with its place (#) in each — ✕ takes it off one, **+ on another alignment…** puts it where it fits along that one. A shared point is one point: moved, it moves on all its alignments.
- **Delete** (tool) deletes a point: off every alignment it is on (asked first when on several); the other points keep their order. An alignment may be left without points.
- **View › Work on route** (yours only): the profile shows that route, the checks (clearances) and the structure loads keep to it, and everything else is drawn faded in the 3D view and the plan.

Files and projects of older versions are read into this form once (see [line file](line-file.md)): each alignment's points become points of their own, shared where alignments met; an alignment on several routes becomes one per route.

## Library editors

**A project keeps its libraries.** The wire library, the structure types, the insulator assemblies, the weather and load case files, the structure models (`.ohlfe`) and poles (`.ohlp`), the section library (`.ohlsec`, the profiles the structure models' members refer to: see [Section library](section-library.md)), the clearance rules (`.ohlr`), galloping parameters (`.ohlg`), thermal ambient cases (`.ohlta`) and unit costs (`.ohlcost`) are stored in the project file (`.ohl`), so the project alone is everything needed to open it elsewhere. Opened the first time, each kind the project does not hold yet is copied into it from where it was read (the files given, next to the project, or the default folders; structure models and poles from the structure folder, the section library from the `Sections/` folder next to the project, else the `.ohlsec` files next to it — never the shipped example; the others from next to the project); the line's structure checks (**fe**) use the project's section library; a library given on the command line (`--library`, `--structures`, `--insulators`; `--weather` adds its file) replaces the project's. Every save of a library page or of the weather case table goes into the project. **File › Export › Libraries…** writes them all as files into a folder (a folder per kind), and **Export…** on a page writes the file open: to share them, or to compare them with other data. A user who may not change the project (a viewer) reads the libraries from their files as before. (The model reads working copies in a temporary folder; the project is what is kept.)

The **Structures**, **Sections** and **Criteria** menus open an editor for the wire library (`.ohlw`), insulator assemblies (`.ohli`), structure types (`.ohls`) or weather cases (`.ohlwc`) — first the files the model reads: the wire library given or next to the model, `Structures/` next to it, the insulator directory, the weather case file. Choose one of them, **Browse…** for a file anywhere on the computer (in a project: copied into the project; while the library is empty it starts at the examples shipped with OpenOHL — `libraries/cables`, `libraries/insulators`, the starter template's structure types, weather and load cases: invented or typical values, not for design), or **New file…** to create one from a template (in a project: in the project, under the name chosen). An empty library says so on its page. Where a cable is chosen (a section's or a jumper's window) and the wire library is empty, the window says so with **Open the wires library**; the Structure loads page without a load case file says so with **Open the Load cases library**. For wires and weather cases the list on the left holds the items (**Add**, **Duplicate**, **Delete**).

**Use for the model** makes the model read the file open: the wire library or the weather case file itself; the folder of an insulator or structure type file. The model is solved again; a wire library without every cable the line uses is refused (the cables missing are named) and the model keeps its own.

A cable starts with its **model** — a list of the three cable models (non-linear; linear with creep proportional to the creep case tension; linear with a temperature increase) — and the **Bimetallic conductor** tick (a core with its own data; unticked, the core goes): choosing a model adds the fields it needs (the outer and core curves with their creep curves, or the creep temperature shift, and its tension) with example values, fields it does not use are hidden (kept in the file), and the fields a cable or its model needs cannot be removed (their 🗑 is greyed). A bimetallic cable has its own behaviour above the transition temperature, below the tick: its outer strands go into compression up to its maximum virtual compressive stress, or take none (bird cage). Sections written as `[cable.outer]` tables are edited like inline ones.

Every field is shown as written in the file, with its units (`"28.1 mm"`, `"55 GPa"`, `"-5 °C"`); numbers and lists as TOML (`23e-6`, `["clearance", "loads"]`). **add a field…** offers the fields of that kind not yet given, with an example and their meaning; 🗑 removes one. A structure type's points, wire points and strings (and version 1 attachments) are listed below its fields (add, duplicate, remove); its body and design — joints, members, materials, sections, generators, the pole, extensions, load cases — are named there and edited in the [structure application](structure-app.md) (**Open this type in OHL-Structure…**). Comments and layout of the file are kept.

### The structure screen

The **Edit** tool on a structure (or a right-click with it), and
**Strings and points…** in a structure's properties, open its **structure
screen**: for a typed structure, its type on the Structure library page
(**Pylon**, next to **Fields**); for a structure without a type, the
**Structure editor**. The screen is split: the **tables on the left**,
the **pylon in 3D on the right** — drag the divider between them (it
starts at about 45/55 and keeps its place while the program runs).

Only the basics are edited here: the **attachment points**, the
**strings** (insulator, length, weight, compression, strain) and the
**wire points with their sets**; with the structure's name, type,
extension and height adjustment in its properties and its **Placement…**
window. The body — joints, members, sections, materials, supports,
generators, the pole, extensions — and the design (load cases, analysis)
are drawn in the view for context and edited in the [structure
application](structure-app.md): **Open this type in OHL-Structure…**
at the top of the screen.

- The top line gives the **level** worked out from the file ([detail levels](structure-library.md#detail-levels)), the counts of attachment points, strings, wire points and sets, how many structures of the line use the type (they follow when it is saved) and **Open this type in OHL-Structure…**; below it, how many joints and members the body has.
- **In the view** (x to the right of the line red, y ahead green, z up blue, 0;0 at the centre, the ground grid at the level of its feet): drag to turn, right-drag to pan, the wheel to zoom, **Fit** to see it whole. A click picks an attachment point (orange) or a wire point (blue, with its set); **Shift + click** picks another. Joints and members are not picked here: members with a section are steel grey, without one (sticks) sand-coloured; supported joints green. A member clicked on a structure of this type in the line's 3D view is shown picked here.
- **Drag** an attachment point or a wire point to move it, in the plane facing you; it snaps to the **snap** grid (default 5 cm; 0: none) or onto a joint near the pointer. A point on a joint or along a member moves with the body: the screen says so (move it in the structure application).
- **Drag handles in the line's 3D view.** While a structure's screen is open (the Structure editor of a structure without a type, or its type on the Structure library page) and that structure is selected (or one of its strings, wire points or points), the line's 3D view shows **handles** on it: its attachment points (orange), its wire points (blue, where the tables put them — before stringing) and, for a type with a body (levels 2 and 3), its joints (grey squares). The pointer over a handle enlarges it and writes its name and its coordinates in the structure's axes (x across, to the right looking ahead; y ahead; z up from its base). In the Minecraft scheme too, with the mouse free: a press on a handle drags it instead of capturing the mouse.
  - **Drag** an attachment point or a wire point to move it. Free, it moves in the plane facing you. While dragging, **X**, **Y** or **Z** hold it on that axis of the structure (a line in red, green or blue shows the axis), **Shift + X / Y / Z** in the plane across that axis; the same key again frees it. It snaps onto another point, wire point or joint of the structure near the pointer, else to the screen's **snap** grid (default 5 cm; 0: none), in the directions it may move; hold **Alt** to move it without snapping. Beside it the view writes where it is (x, y, z in the structure's axes), how far it moved, what it is held to and what it snapped onto. **Esc** cancels the drag: nothing changes. The camera keys do not fly the view during a drag.
  - Released, the change is **one command** (one undo), as typing it would be: an attachment point takes its new place (as in the Attachment points table) and takes along, by the same displacement, the wire points hanging from it — those whose strings all hang from that point (and what hangs below them), whether given by their string's length and direction or by their own position: their strings keep their length and direction. A wire point also held by a string from another point (a **V**) does not move: its strings from the dragged point change length, and the status bar says so (*wire point W2 also held by a string from elsewhere (a V): not moved, string S2 changes length*). A wire point moves with what hangs below it (as in its string window: the strings holding it change length). A point or wire point that comes from the structure's **type** becomes the structure's **own**, over its type's — the status bar says so (*point A1, wire point W1, string S1 now the structure's own, over its type's*: a point of the type takes the wire points that follow it, with their string windows, as the structure's own too); a wire point takes the strings and wire points of its string window with it, as that window does. The type's file is not changed. The line is solved again as after any edit, and the Structure editor shows the structure as it is now.
  - **Not dragged**: joints — they are shown, and edited in [OHL-Structure](structure-app.md) only — and attachment points sitting on a joint or along a member, which belong to the body and move with it there; the status bar says so (*joint J1 is not dragged here: joints are edited in OHL-Structure only*). A drag also waits while the Structure editor has changes not applied, or while a window editing that structure (its strings, its placement) is open — apply or cancel them first (the drag would not keep them).
- **+ Attachment point** adds a free one (mirrored across from the point picked, else at the top of the centre); the **I** and **V** presets hang an insulator of the length given from the point picked (or a V from the two picked) to a new wire point — its set is put by hand in **Set points** (only pylon templates number sets themselves); **Delete…** lists everything that goes with what is picked (a point: its strings) and asks.
- **Tables**, what hangs on the structure:
  - **Attachment points** — where insulators hang on the structure: a position, or the joint or member they sit on; free ones moved here (dragged, or typed); how many insulators hang from each. Moving one takes its insulators' wire points along.
  - **Insulators** — each string: what it **hangs from** (an attachment point, or another insulator's wire point: a TAK), its **wire point** (where it ends; another insulator's makes a V), its **kind** (suspension: the wire runs through its set; strain: the wire ends there), an **assembly** of the insulator library (its length, weight, wind area; a strain assembly makes it strain) or none and a **length**, its **angle** from straight down (0° hanging, 90° level) and **direction** in plan (in the project's angles), weight, wind area, the compression it may take, a description. The length and the angles **place its wire point**; a V's legs show their directions (they follow where their lengths meet). There is no "ahead" or "back": the angles alone say where it points. **+ New insulator** hangs one from the point picked (the length given) to a new wire point; **From the library…** hangs an assembly of the library there; **Save to library** (on a row) writes that insulator as an assembly of the insulator library (a V's leg as a V-string assembly); **🗑** deletes it (its wire point with it when nothing else is on it); **Insulator library…** opens the library to import, export, edit or delete assemblies.
  - **Wire points** — where an insulator ends: their position, placed by their insulator(s) (typed only for one no insulator reaches: fixed), the insulators holding each and those hanging from it, its set, a counterweight.
  - **Set points** — where a wire is strung: the **set** number (typed by you; unique on the structure), the **wire point** it is on (moved to another with this list), its **kind** from its insulator (suspension or strain; fixed without one), 🗑 to take it off; **+ Set on wire point…** puts one (the next free number) on a wire point without a set. On a structure (Apply), a set renumbered takes the sections and jumpers strung there along — two sets swapped too.

  The file's other fields are in **Fields**. Hover a column title for what it means.

**A structure without a type** opens on the same screen, the **Structure editor**, in a window of its own (drag its tab into the main window to dock it), with its points, wire points, strings and stick drawing in its own axes. Nothing changes on the line until **Apply** (one command, one undo); **Revert** goes back to the structure as it is. **Make it a type…** saves it as a structure type of the project (in its structure types folder, else a `Structures` folder next to the line), gives the structure that type — its points and strings then come from the type — and opens the type. Schemes are data (`controls.rs`: actions bound to keys and mouse buttons), so schemes familiar from other software can be added as presets, and later edited and saved.

The **plan** pans with a drag of any button and the **profile** moves along the route with one; their clicks follow the same option (left: select, right: use the tool — or the other way round), and their double-click (plan: select and centre on it; profile: show the whole route) is a double-click of the button that selects.

**Edit › Snap: what can be clicked** chooses what can be clicked: structures, spans, jumpers, wire points and string tops (selecting their set), alignment points, LiDAR points (more kinds will be added); by default structures, spans and jumpers. At about the same distance, a point wins over the line it sits on and a structure over a wire. The choice is remembered.

Clicking an object in any view selects it everywhere: a structure anywhere along the lines it is drawn with (mast or stick drawing, arms), a **string** anywhere along it where it is drawn (as solved in the case shown — with the wind from both sides, each of the two; a jumper's helping strings too; its properties give where it hangs, its wire point, set, length, weight, wind area, dead end and its force in the case shown), attachment points (Snap) where the clamps are drawn, a span anywhere along its wire, a jumper anywhere along it (drawn as a bundle like its section). The properties of a jumper show its cable, section, bundle (and whether it is its own or its section's), length or sag, support string or helping strings, results in every weather case, and the force in each string holding a support clamp in the case shown ("slack" when it is), in a box of fixed height. In the 3D view the strings holding a jumper's clamps are drawn to the clamps as solved, and each clamp as a short bar along the jumper. Tabs can be dragged to rearrange the window.

Loading runs in the background. On a real 25 km line with 99.6 million LiDAR points stored in its project, the window is ready in about 8 s (release build): the whole cloud decoded (every one of its 31 classes shown, 2.1 million points), a 5-million-triangle ground surface.

## Plugins

Plugins › **Plugin manager…** lists the plugins found: those installed for you (in the application's data folder, `plugins/`) and those of the folders you added (used where they are — handy while writing one). For each: its version, kind (WebAssembly or Python), what it provides (a file-format plugin's formats), and why it cannot be used if it cannot (another interface version, permissions asked for that cannot be granted, its entry file missing — e.g. not built). The tick turns a plugin on or off. The folders added and the plugins turned off are kept in `settings.toml` in your plugin folder, **shared with OHL-Structure** (its Plugins › Plugin manager lists the same plugins): changed in one application, the other reads it when its manager opens (here: **Reload**); before that file exists, what this application remembered itself is taken. **Install from a folder…** copies a plugin into your plugins (a WebAssembly plugin's manifest and `.wasm`; a Python plugin's folder); **Remove** deletes an installed copy (after a confirmation). A plugin name found twice is used from the first place (your plugins, then the folders in order).

File-format plugins add their formats to File › Import › Into the line / Export › The line, next to the built-in ones. They run on a worker thread, sandboxed, with time and memory limits ([Writing plugins](../development/plugins.md)).

## Python console

Plugins › **Python console** opens a page with a Python interpreter in the application (Python 3.10+, the one OpenOHL was built with). Type code and press Enter (Shift+Enter: a new line; ↑ ↓: history); the value of a last expression is printed. **Run a file…** runs a script as `__main__`; **Plugin scripts** lists the Python plugins turned on. **Stop** interrupts a script (`KeyboardInterrupt`); a script running longer than the **time limit** (default 300 s) is stopped.

The `ohl` module drives the open project:

| Call | |
|---|---|
| `ohl.line()` | the working line, as in a line file (a dict) |
| `ohl.cases()`, `ohl.case()` | the weather cases, the one shown |
| `ohl.results(case=None)` | the solved sections of a case: per span sag, horizontal and largest tension, mid and low points; what failed |
| `ohl.selection()` | the selection, in words |
| `ohl.apply(command, what=None)` | a session command (as in the operation log, e.g. `{"op": "move_structure", "id": "T2", "position": [x, y, z]}`): validated, logged, undoable; what it touches is solved again. A refused command raises |
| `ohl.batch(commands, what=None)` | several commands as one (all or none, one undo) |
| `ohl.undo()`, `ohl.redo()` | your last command |
| `ohl.status(text)` | text in the status bar |
| `ohl.convert(kind, value, unit)` | unit conversion, as in the `ohl` package |

```python
import ohl
for s in ohl.results("everyday")["sections"]:
    print(s["section"], max(p["sag"] for p in s["spans"]))
```

Each call is answered by the application at its next frame, so a script always sees the line as it is now; many edits go faster (and undo at once) in one `ohl.batch`. A read-only project refuses edits.
