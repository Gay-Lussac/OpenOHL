# Desktop application

`ols-cad` opens a line file or a project and shows it in dockable views that share the selection and the weather case.

```bash
cargo run --release -p ols-app -- examples/synthetic-line/synthetic-line.ols.json \
    --terrain examples/synthetic-line/synthetic-survey.csv \
    --weather examples/synthetic-line/weather-cases.olswc

cargo run --release -p ols-app -- project.ols          # with the project's point cloud
cargo run --release -p ols-app                         # the start page: File › New project, Open
```

On macOS, double-click **Start OLS CAD.command** at the top of the source tree: it builds and starts the app on its start page (new project, open, the files opened recently). Libraries given on the command line apply to the file given there only; files opened from the File menu use their own (a project's are kept in it).

| Option | Meaning |
|---|---|
| `--library` | Wire library (file or directory); default: the `*.olsw` files next to the model, else `libraries/cables`. |
| `--structures` | Pylon files; default: the `Structures/` folder next to the model. |
| `--insulators` | Insulator library directory. |
| `--weather` | Weather cases (`.olswc`); default: still air at 15 °C. All cases are solved. |
| `--terrain` | Survey points for the ground. |
| `--pointcloud` | Point cloud in a project (`FILE.ols` or `FILE.ols#name`) or a COPC file (`FILE.copc.laz`, streamed by node, see [Point budget](#point-budget)); default: the project's own. |
| `--points` | About how many LiDAR points are shown (default 2 000 000). Points of **every class** of the whole cloud are shown, ground classes and noise included: a class of up to 20 000 points whole, the larger classes thinned alike to the budget. The ground surface is built from all points of the ground classes (lowest per 1 m cell) in the corridor. |
| `--corridor` | Half width of the corridor around the spans the ground surface is built in (default 60 m). |
| `--user` | The user editing the project (default: the login name), see [Editing](#editing). |
| `--rules` | Clearance rules (`.olsr`) for the Clearances tab; default: the only `.olsr` of the project (next to a line file). |
| `--load-cases` | Load cases (`.olslc`) for the structure loads; default: the project's own, else the first `.olslc` next to the file. |
| `--class-scheme` | LiDAR class scheme (`.olsc`: class names, roles, colours) used instead of the point cloud's own. |
| `--controls` | Navigation scheme: `orbit` or `minecraft` (default: the one used last). |
| `--screenshot FILE.png` (`--focus ID`, `--distance M`) | Load, render the 3D view to an image and exit (with `--focus`, looking at that structure's first wire point). |

**Weather cases are solved when needed:** opening a model solves only the weather case shown first. Another case is solved in the background the first time it is shown (Display weather cases, a section's own display case); the status bar says which are being solved. A check or a script that needs a case solves it first. Edits re-solve the cases already solved; the others are solved from the line as it is when they are first shown. The Model page lists the cases not solved yet.

**Opening a menu stops what was going on**, as Escape would: a captured mouse is freed, a wire being strung or an alignment being laid out is given up, so the menu's commands work on the first click.

Under it, the **quick bar**: the line's name, the selection, then the commands chosen for it (default Undo, Redo, Fit views, Run checks). **⚙** (or View › Customize the quick bar) adds any command of the menus — commands, library editors, tools — removes and orders them; the bar is remembered.

**Pages** work like browser tabs: each has a tab with a close button; drag a tab to rearrange, or out of the window to make a floating, resizable window with its own row of tabs (drop more pages on it). Closed pages come back from View. Library editors open together in a floating window.

## Views

- **3D** — ground (shaded), LiDAR points coloured by class role (vegetation green, buildings red, water blue, wires yellow…), structures, insulator strings, wires in their phase colours (bundles as their subconductors, `bundle_spacing` apart — one section, solved and selected as one — held at every clamp by a yoke: a bar for two, a triangle for three, a polygon for more; the back and ahead spans and the jumpers end on its corners), alignments. Navigation: see [Controls](#controls). Height exaggeration in the Model panel.
- **Plan** — alignments, wires and structures from above, north up, with a scale bar. Drag, scroll at the pointer, double-click to centre.
- **Profile** — per route, or **All alignments, in order** (the first, then the second… each starting where the one before ends, its name at the start): ground along the centreline, structures and wires by station. **corridor ±** (m, yours only) shows what lies that far left and right of the alignment: the ground at both edges (thin, darker), the survey points of the ground surface (dots) and the 3D lines and points of the drawings (DXF, in their colours; flat 2D drawings have no heights and are left out; hidden drawings are not drawn), projected on the profile; 0 shows the centreline only; heights fit the visible stretch, or keep the ratio chosen in View › Profile aspect ratio (written at the top left). Scroll zooms at the pointer (at a fixed ratio the height under the pointer stays under it), drag moves (also up and down at a fixed ratio), double-click shows the whole route.
- **Properties** — the selected structure (position, type, attachments, spans through it) or span (cable, circuit, electrical system and voltage, bundle, horizontal and maximum tension, sag and lowest point in every weather case). Links select related objects.
- **Model** — layers, sections or jumpers that failed to solve, by weather case (click one: that case is shown, the object selected and the views brought to it), what was loaded and how long it took.
- **Clearances** — clearance violations of the shown weather case (see [Clearances](#clearances)).
- **Properties** of the other kinds: a wire point with a set (its strings — top, wire point, length, weight, insulator, compression —, spans and jumpers there), an alignment point (position, tied structure), a LiDAR point (position, class and roles).

## Level of detail

The 3D view draws the large layers — terrain, LiDAR points, structures, wires, other weather cases, other project lines, DXF drawings — in **chunks**: the 256 m tiles of the project grid (the grid of the project file's spatial index). Every frame, each chunk in view is drawn at a **level of detail** from its distance to the eye; chunks outside the view or beyond the layer's render distance are not drawn, and those far beyond (1.5 × the render distance) leave the GPU. Missing chunks are built nearest first, a few milliseconds per frame, so the view never freezes: until a chunk's level is built, a level already built is drawn. An edit rebuilds the layers of the line, not the terrain and the LiDAR points.

**View › Level of detail** (a page) is the table of these settings, a row per layer, every value typed in, remembered with the window layout:

| Layer | Level 0 | Level 1 (default from) | Level 2 (default from) | Render distance |
|---|---|---|---|---|
| Terrain | every TIN triangle | the surface on an 8 m grid (1.5 km) | a 32 m grid (5 km) | 30 km |
| LiDAR points held in memory | the share of the survey chosen in Survey data display options (default 25 %; 100 %: every point) | 25 % of that (500 m) | 5 % of that (1.5 km) | 3 km |
| Structures | lattice, arms, strings | mast, arms and strings (2 km) | the mast line (8 km) | 50 km |
| Wires, other cases, project lines | every point; bundles as subconductors with their yokes | 16 points per span, one line per bundle (1.5 km) | 5 points per span (6 km) | 50 km |
| Drawings (DXF) | every vertex and point | lines simplified to 0.5 m, lines and points smaller left out (1 km) | simplified to 2 m (4 km) | 10 km |

The last column of the table shows what was drawn in the last frame: the chunks at each level, of how many, and how many are still loading. On a 25 km line seen from 1.5 km, 5 million terrain triangles became 280 000 drawn, 1.5 million LiDAR points 24 000, and 190 000 wire segments 14 000; every chunk builds in under 2 ms.

### Point budget

A survey stored in the project — or a COPC file opened as the point cloud (`--pointcloud survey.copc.laz`) — is not drawn by the table's levels but **streamed by node under a point budget**. Its nodes are, for a stored survey, each 256 m square at four levels (about 1/64, 1/16, 1/4 of its points, then every point: the [levels of detail](project.md#levels-of-detail) stored in the project), and for a COPC file its octree. Every frame:

1. the nodes in view and within the LiDAR row's render distance are taken, the coarsest first;
2. a node whose points lie farther apart on the screen than the **error** allowed (default 1.5 px) is refined — its finer level, or its octree children — the one with the largest error (the nearest) first;
3. until the next node would exceed the **point budget** (default 5 million points; the share of Survey data display options thins every node further and counts in the budget).

The missing nodes are read on background threads (half the cores, at most four), each with its own reader of the project file, in that order; the queue is replaced every frame, so it never lags behind the camera. Until a node is read, a coarser (or finer) level of its square already read is drawn. Nodes read stay on the GPU while they are in view; beyond 1.5 × the budget the least recently used are dropped. Classes of up to 20 000 points are read whole at every level (wires, towers); hidden classes are not read.

**View › Level of detail** sets the budget (0.1–200 million points) and the error (0.1–50 px), remembered per user, and shows what the last frame did: nodes drawn of how many, points drawn and wanted, whether the budget was reached, what is on the GPU and still loading.

Measured on an Apple M1 Max (synthetic survey of 25 million points on 2.5 km × 2.5 km, 1600 × 1000 view, error 0.3 px so that the budget limits the view; `point_budget_frame_times`, release build, GPU time included):

| Budget | Points drawn | Read in | Frame while turning (median / slowest) |
|---|---|---|---|
| 2 million | 1.97 million | 0.07 s | 7.7 ms / 9.8 ms |
| 5 million | 4.97 million | 0.13 s | 16.5 ms / 19 ms |
| 10 million | 9.9 million | 0.23 s | 32 ms / 35 ms |

The frame time grows with the points drawn (about 3.3 ns a point on this GPU), not with the size of the survey: what a frame touches is bounded by the budget and the nodes in view (choosing them takes microseconds). For 60 frames a second, keep the budget near 5 million on such a machine. A survey of 10⁹ points on disk has more nodes (a few thousand for a 100 km corridor), read the same way: the index of its blocks once when the view opens (about 0.4 s per 10⁵ blocks; 10⁹ points are some 10⁵), then each node as it comes in view. Not measured at that size here (only synthetic data is used for performance, and the largest run is 25 million points). The synthetic grids also compress to almost nothing: real surveys decode several times slower than the 25–45 million points a second measured above, so expect nodes to arrive a few times slower — the frame rate does not depend on it.

The level of detail changes what is **drawn** only: calculations, checks, the profile, the plan and picking always use the full model.

## Weather cases shown

**Display weather cases** (Criteria menu) chooses how the wires are shown:

- **The same weather cases for every section**: tick one or several (the list scrolls in a box of fixed height); every section is drawn in each case ticked. Display only — the Sections table's display cases are kept (not used while this is chosen).
- **Each section's display weather case (Sections table)**: every section in its own display cases; sections without one in the cases ticked above. Setting display cases in the Sections table chooses this too.
- **Wind**: from the right, from the left, or **both sides** (each case with wind solved and drawn twice; the wind from the right is the one checked). The side the wind comes from is a display choice, not part of the weather case.

Wires are drawn with their jumpers, yokes and **insulator strings, to their clamp as solved in each case** (swung by the wind, moved with the temperature). Labels (section labels, sags, structure labels) are written once per section, in its first case: the other cases show their wires only. In 3D, labels are written only within a distance of the eye — 1500 m unless set otherwise in either Display options menu ("3D labels within … m of the eye") — and are not even built beyond it, so a long line stays fluid. Every copy drawn can be clicked — anything that moves with the weather case — a span, jumper, string, wire point, span point or spacer — in any of the cases shown (either wind side) — and selects the object (Edit opens it as usual). The selection is highlighted in every case it is drawn in, the copy clicked the strongest, and its properties mark the case of that copy (▶, coloured) in their list of weather cases. The first case is the one checked for clearances. These choices are yours, remembered with the project on this computer. In the properties, a span's or jumper's results in every weather case are listed in a box of fixed height, scrolled.

The model's **weather case file** is remembered with the project (`--weather`, or **Use for the model** in the Weather cases library editor, Criteria menu): opened again without `--weather`, the project uses the file it used last.

## Project lines

A project holds several designs of the line — the **main line** and, for example, the **phases** of the project — each edited on its own. You work on one at a time (Versions › Project lines…, or the Versions menu): your edits and Undo apply to it; others are shown next to it in their colour. A new line is a copy that then lives its own life; **Bring in changes** updates it from another line, and a phase goes back into the main line through a review. On a server each user chooses their own line. Everything is described in [Project lines and phases](project-lines.md).

## Saving

Every edit is stored in the project file as it is made (the operation log), so nothing is lost when the app stops. **⌘S** (Ctrl+S on Windows and Linux, or File › Save) writes the project file through, saves the library pages with changes that read (the model reads them again) and says which table changes are still pending (Apply makes them). **⌘Z** / **Shift+⌘Z** (Ctrl+Z / Shift+Ctrl+Z) undo and redo, outside text fields.

## Editing

A project (`.ols`) opened by a user with the designer or admin role (`--user`, default the login name) can be edited; every edit is a command in the project's log, undoable per user (ADR-0005). A line file, or a user without a role, opens read-only — the status bar says why.

| Action | How |
|---|---|
| Move a structure | **M** (or the Move tool in the hotbar), then right-click a structure in any view: the **Move structure** window shows E, N, z (or "base on the ground"); the change is previewed live (the shown weather case re-solves the sections through it); **Apply** (Enter) makes one command, **Cancel** (Escape) puts it back. |
| Delete | The **Delete** tool and a right-click on a structure, a string (its insulator or wire point), a span (deletes its section) or a jumper — or **Delete** / **Backspace** for the selected one. When it takes other objects with it (a string: the sections through it and their jumpers; a structure: its sections, jumpers, routes…), a window lists them; **Delete all** applies it as one command. A string of a structure type is left out of that structure (`omit` in the line file). |
| Edit | The **Edit** tool and a right-click: on a structure, its [structure screen](#the-structure-screen) — as **Strings and points…** in Properties: the tables of its attachment points, strings, wire points and sets beside its pylon in 3D (a typed structure: its type, every structure of the type follows when saved; a structure without a type: the structure editor); its body and design: **Edit in the structure application…** there, or **Edit…** in Properties. ## Tools: hotbar and inventory

As in Minecraft, the bottom of the 3D view holds a **hotbar** (it goes with the 3D view when another page is in front; the inventory shows it to arrange it) of nine tool slots. Choosing a slot — **1–9**, a click on it, or the **wheel** while the mouse is captured in first person, one slot per wheel notch (a trackpad steps at a steady pace; Ctrl + wheel stays the speed) — only *holds* its tool; a **right-click** on an object uses it (in first person, on what is under the crosshair): Select, Move structure (M), Delete, Go to structure (G), Edit, Add structure, Add string, String wire, Add alignment point, Add jumper, Add on span, Replace structure (see [Editing](#editing) and [Routes and alignments](#routes-and-alignments)). A left click always selects; a right-*drag* still pans. A window opened by a tool (Move, an editor, the confirmation of a deletion, Go to) frees a captured mouse and opens at the crosshair (or at the mouse outside first person), also when it replaces a window already open for another object; it can be dragged anywhere, also partly off the screen. **E** opens the **inventory** with every tool (**E** or **Escape** closes it); only while it is open can the hotbar be arranged: drag a tool onto a slot, drag slots to swap them, drag a slot back to the inventory (or right-click the slot) to empty it. The arrangement is remembered. New tools are added to the inventory as they come.

## Clearances

The **Clearances** tab checks the shown weather case with a rule file (`.olsr`, the format of `ols line --rules`; see [Clearance rules](terrain.md#clearance-rules-olsr)): the wires against the ground surface, against the LiDAR points of the rules' classes, and against the line's other wires, with the requirements by voltage of each section's electrical system. Rule files are listed from `--rules FILE` and the project's `.olsr` files (next to a line file); the one given or the only one found is chosen at start.

Checks run **on demand**: **Run checks** (Checks › Wire clearances, or the quick bar) or **Check now** in the tab; tick "after every edit" to check again after each edit and change of weather case. The check runs in the background. LiDAR points are read again from the project's point cloud each time, only those of the rules' classes in a corridor around the spans, so nothing more is kept in memory: on the 25 km line with 18.8 million such points a check takes a few seconds. The list shows each violation, worst first: wire (span or jumper, and the other wire for wire rules), rule, vertical or radial clearance against the requirement, the LiDAR class, how many points are too close. Clicking one selects the wire and brings the views to it. The violations are drawn in red in the 3D view (a line from the wire to the point too close; layer "Clearance violations") and circled in the plan.

Rules for other lines and rules across pairs of weather cases are run by `ols line` only; the tab says so.

The **Analyses** entries of the Checks menu open windows that compute on demand in the background, each with a results table (click a span to go to it) and CSV export — see [Galloping, blowout, vegetation and as-built wires](analyses.md): **Galloping ellipses** (a `.olsg` parameter file and a weather case), **Vegetation** (the point cloud's vegetation classes near the wires of a case, growth, trees falling in), **As-built wires** (catenaries fitted to the wire points, the temperature at the survey).

### Vertical and radial clearances

**Checks › Ground clearances** opens two windows: **Vertical clearances…** and **Radial clearances…**. Each checks the spans and jumpers against its own list of rules. The window can be closed at any time; closing it stops a check that runs.

**The zone.**

- **Vertical**: an area of points straight under (and over) the wire: **width on each side** (default 1 m) across the line, in plan, and **depth** (default 0.2 m) along it. The clearance is the shortest vertical distance between the wire and a point of the area: a point is compared with the wire's lowest point within the depth around it (its highest for a point above the wire — rare, but measured the same way). Bundles: the lowest (highest) subconductor. A rule may have **its own width** (the rules' **width m** column: click the window's width, shown in brackets, to give the rule its own; × goes back to the window's).
- **Radial**: the direct 3D distance from the wire, to each subconductor of a bundle.
- **Ignore LiDAR points farther than … m from the wires** (both windows; unticked: as far as the rules reach): only the points within that distance of the wires are read and compared.

**What is solved.** **Circuits**: the circuits checked, ticked by circuit name (none ticked: every circuit). **Solved by**: each section's own calculation (the default), or every section by **finite elements** or by **ruling span** for this check (each keeps its cable condition).

**The rules.** One row per rule: a name, the **voltage** of the wires (any, or one of the line's systems; earthed wires are 0 kV), the **weather cases** (ticked; none ticked: every case), the **distance** to keep (m), the vertical window's **width** (the rule's own, or the window's), the **wires** checked (the sections' spans, the jumpers, or both — the default) and the **targets**: LiDAR classes ticked from the point cloud's classes (the class scheme's when no cloud is open), and the **ground surface**. You never type a class number. **Add rule**, **Duplicate** and **Remove** (it asks first) edit the list.

**Load preset…** lists the clearance presets of the project — given by a design-code plugin when it generates (Criteria › Design code, see [Design codes](design-codes.md#clearance-presets)): a rule file and a weather case file of the same name among the project's libraries, with rules of the window's kind. Choosing one replaces the rules listed with its rules, and takes its wind, circuits, calculation method and search distance; its weather cases missing from the model are added to the model's weather case file (the model's cases of the same name are kept). Everything can be changed afterwards — the classes, the cases, the distances — and is kept as the window's rules.

**Import… and Export…** read and write rule files (`.olsr`, see [Clearance rules](terrain.md#clearance-rules-olsr)). A row is written as one `[[rule]]` per target kind (classes, ground), with `voltages`, `wires`, `cases`, `vertical_band` (the width: the rule's own or the window's), `vertical_depth`, a `[wind]` table and a `[check]` table (the circuits, the method and the search distance, when set), so `ols line --rules` reads the file too (it ignores `[wind]` and `[check]`). Importing keeps the ground and point rules with a clearance of the window's kind; a requirement by voltage gives one row per voltage of the line; roles become their classes; the first rule's `vertical_band` becomes the window's width, another one a rule's own. The window says what it left out (rules between wires, exclusion zones).

**Without the window.** `ols zones --rules FILE` runs the same check from the command line on a window's rule file or a preset, with the project's point cloud and ground (see [`ols zones`](terrain.md#vertical-and-radial-clearances-without-the-window-ols-zones)).

**Where they are kept.** Like the Clearances tab's rule files, in the project: `<model>.vertical-clearances.olsr` and `<model>.radial-clearances.olsr` among its clearance rules (next to a line file). Every change is kept when the mouse is released. The Clearances tab lists these files too; **File › Export › Libraries…** writes them out (folder `rules`) for `ols line --rules`.

**Wind.** A weather case with wind is solved with the wind from **the left and the right** (default), **the left only** or **the right only** — looking ahead along the line. Untick **Step the wind** to check only the case's own pressure. Tick it to solve every pressure from 0 up to the case's, in steps of **step Pa** (default 50 Pa, at most 200 steps per case and side). The wires at all these positions form the surface the wire sweeps as the wind rises; each span's clearance is the lowest over all of it.

**Run** solves the wind positions on all cores and checks them in the background, with progress (**Stop** ends it; the time budget is 15 minutes). LiDAR points are read again from the point cloud, only those of the rules' classes near the wires (within the search distance when one is set). The results list the spans below a rule, worst first: span, rule, required and found distance, the wind pressure and side, the target (class or ground) and how many points are too close (each counted once over all wind positions; for the ground, wire pieces at the worst position). Click a span to select it and bring the views to it. The violations are drawn in red in the 3D view (layer "Clearance violations") and circled in the plan. On the synthetic example, 121 wind positions (600 Pa in 10 Pa steps, both sides) are solved and checked in under 0.1 s.

The small striped button at the left of the cell opens the [colour tool](#colour-tool); its **OK** writes the colour in the cell as a change (pending until Apply). A colour picked for a default sets it, even the same colour.
- A changed cell turns yellow and stays **pending**; **+ Add row** adds an object typed in a green row (🗑 removes it); 🗑 on a row marks it for deletion (struck through; click again to keep it). **Apply N changes** makes one command for all of them (one undo, ⌘Z), with the same checks as the editor windows — a cell that does not read is named and nothing is applied; **Revert** drops them. When the changes reach further than the rows changed, everything they also change is listed first and **Apply all that** confirms:
- deletions that take other objects with them (a structure's sections and jumpers, a string's sections…);
- a section's circuit name, phase or system, which also go on the other sections of its circuit.
- **Renaming** a structure, section, jumper or system, or renumbering a string, keeps its place, and what refers to it follows (section points, jumper ends, routes, tied alignment points, sections' system).
- Sections: changing the **condition** needs its value; **status** clipped in computes the lengths of its condition (as the section window does); **points** restring it. **Display cases** draws the section in each weather case listed, separated by `;` (e.g. `max temperature; glaze ice`), in every view; the first one is the one picked and reported in the properties (empty: the case shown) — sections can be shown each in their own cases. **H kN** and **max sag m** give one value per display case (`12.31 / 9.87`); typing one number is a **target** in the first display case: the section's condition (tension or sag) is found that gives it (a section clipped in must go back to the blocks for that).
- **#** orders alignment points and weather cases: `3.5` goes between 3 and 4.
- Weather cases are not part of the project but the model's case file: **Apply** writes it (comments and layout kept, values with their units) and the model is solved again; not undone with ⌘Z. Without a case file (the default 15 °C case), a project takes new cases in the table: **+ Add row**, then **Apply** writes its first case file (the 15 °C case and those added) and keeps it in the project. A line file without one: make one in the Weather cases library editor (Criteria menu) and choose **Use for the model**.
- Click a column title to sort (again: descending, again: unsorted). Numbers sort by value, and names in natural order, the numbers in them counted as numbers: sec2, sec10, sec100 (not sec10, sec100, sec2), whatever their leading zeros. the filter keeps rows with the text in any cell. **⤴** selects the row's object and brings the views to it (a weather case: shows it). A page with pending changes shows * on its tab and does not close.

### Structure picker

A window to choose a structure type, opened from the type button of the structure window (Add structure, Edit) and from the type cells of the Structures table. On the left, a table of the library's types, one row each: **id**, **name**, **kind** (lattice, pole, portal, other), **level** (1 stick figure, 2 outline, 3 full design: from what the file holds), **sets / wires** (sets of wire points, wire points), **height** (of the highest point above the feet), **extensions**, **description** (the notes at the top of the type's file, else where it comes from; hover for all of it) and **used** (structures of the line with this type). A click on a column title sorts by it (again: the other way). The **filter** at the top keeps the types with every word typed in their id, name, kind or description (any case); it has the keyboard when the window opens, and is remembered until OLS CAD closes. The type in use is selected and in bold; the first row is **no type** (the structure's points given in its window).

On the right, the selected type drawn: its **front** (across the line) and **side** (along it) views at one scale, the feet on the ground — members and body lines, strings (blue lines), points where strings hang (orange), wire points (blue) — or, with a GPU, **3D** (drag turns it, the wheel zooms, a double-click fits it). Under it its full name, id and kind, description and source, sets, wire points, height and how often the line uses it, its **level** and what it lacks for the next one (e.g. *For level 3: 12 member(s) without a section*), and its **extension**: tick the base or one of them.

**Choose** (or **Enter**, or a double-click on a row) takes the type and the extension; **Cancel** (or **Escape**, or closing the window) changes nothing. A table of many types scrolls; the buttons stay in view.

### Colour tool

A small window to choose a colour. At the top, **Wheel** or **Sliders** (your choice is remembered):

- **Wheel**: click or drag on the wheel. Round it is the hue (red to the right, green up left, blue down left). Outwards is the saturation (grey at the centre). The slider below is the brightness.
- **Sliders**: red, green and blue (0–255), and hue (°), saturation and brightness (%).

Below, the **old** and the **new** colour side by side, and the new one as `#rrggbb` (type one there too).

The **palette** is your list of colours, in a box that scrolls. Each has a name, its colour and what it is used for (e.g. "380 kV circuits", "earth wires"). A click takes a colour; a double click takes it and closes the tool. Type a name and a use and press **+ Add** to add the new colour. ⏶ ⏷ move a colour, ✏ edits its name, use and colour, 🗑 deletes it (asked first). **Defaults** adds the program's own colours (phases, wires without a phase number, electrical systems) that are missing.

**Export…** writes the palette to a file to share. **Import…** reads one: replace your palette, or add the colours not in it yet. A file that does not read is refused, with what is wrong. The file is TOML (`.olscolors`):

```toml
format = "ols-colors"
version = 1

[[color]]
name = "Phase 1"
color = "#e4572e"
description = "380 kV circuits"
```

The palette is yours: remembered on this computer, not in the project. **OK** uses the new colour; **Cancel** (or closing the window) changes nothing.

## Routes and alignments

A line is laid out in three steps, kept as three kinds of record in the project: a **route** (a path of the line), its **alignments** (each on exactly one route, in their order along it) and the **alignment points** (PIs) of each alignment, in order. An alignment cannot exist without its route. A point is an object of its own: it may be on no alignment yet, on one, or on several — with its own place (order number) in each. Where alignments of different routes meet they share the point, so the point — and a structure tied to it — is on all their routes. Structures, sections, jumpers and what hangs on structures are put on routes **from the alignments**, nothing to keep by hand:

- a structure tied to an alignment point, or within 5 m of an alignment, is on that alignment's route;
- a structure away from every alignment (a crossing line) is on no route until you give its route(s) — in its window (Edit, or when placing it) or the Structures table's **routes** column; it is said in yellow after an edit, and in its properties;
- a section is on the routes of its structures (one running from a route into another is on both), a jumper on those of its two ends.

**A new project** starts with these steps (its first window): 1. **the route** — its name and description; 2. **its alignment** — the New alignment tool is then held.

The points are drawn in the 3D view (cyan, on the ground) and in the plan — those on no alignment too — and can be clicked (Edit › Snap, alignment points). The profile follows every change at once.

- **Terrain › Routes**: one row per route — its id (renaming: its alignments and structures follow), name, description, its alignments in order, how many structures and sections are on it. **+ Add row** makes a route; deleting one asks first and lists its alignments (they go with it; their points stay).
- **Terrain › Alignments**: one row per alignment — its id, name, **route** (a dropdown of the routes; required), its order **#** (3.5 goes between 3 and 4), how many points, description. **+ Add row** makes an alignment (without points yet); with no route yet, **+ New route… / Create the route** above the table makes one. Deleting an alignment keeps its points.
- **Terrain › Alignment points**: a row per point and alignment it is on — its **alignment** (a dropdown), its place **#** there, the point's id, E, N, z, the structure it is tied to, the other alignments it is on with its place there (**also on**), description. A point on two alignments has two rows, each with its own #; a point on none has one row without alignment. A row deleted takes its point off that alignment only (the others keep their order); the point itself is deleted with the last of its rows. (The Delete tool on a point on several alignments asks: **Delete from all** — the point goes — or **Take it off the ticked ones**, its alignments listed with their routes and ticked in a scrolling list; a point on one alignment is deleted as before.) **Alignment ▾** above shows one alignment (or the points on none).
  - **#** orders the points of an alignment (3.5 goes between 3 and 4); another alignment moves the row's point there; none takes it off that alignment (it stays).
  - **+ Add row** with an existing point's id puts that point on the alignment too (shared); a new id makes a new point.
  - Deleting a row deletes the point: it comes off **every** alignment it is on (asked first when on several), the other points keep their order.
- **New alignment** (tool, **E**) lays out an alignment point by point. Each right-click adds a point:
  - **on an alignment point:** that point, shared (a junction);
  - **on a structure:** a new point tied under it;
  - **on a survey point or LiDAR point shown** (within 12 pixels): a new point at its exact E, N and height;
  - **on nothing of these:** a window asks for the point's **E, N and height** (all required; where you clicked is offered).

  **Enter** asks for its route (one: the route worked on, or that of the points it shares, is chosen; **+ New route** makes one — with no route yet, it offers to create one), then makes it (*alignment 1*, *alignment 2*…). **Backspace** takes the last point back, **Escape** gives it up (the tool stays held).
- **Add alignment point** (tool): a right-click on a survey or LiDAR point, a structure (tied under it) or the ground opens its window — its E, N and height (given by what was clicked), and **connect it to the nearest alignment**: ticked, it goes between the two closest points of the nearest alignment; unticked (the default), it is on no alignment yet — New alignment then picks such points one after another, like the String wire tool picks strings.
- **Edit alignment** (tool) changes the course of an alignment. Right-click one of its points, then the new points (snapped as for New alignment; an existing point is shared), then:
  - **another point of the same alignment:** the points between the two are replaced by the new ones (those taken off stay, on no alignment unless on another);
  - **Enter, from its first or last point:** the new points are added there, before its first or after its last;
  - **Enter, from a point in its middle:** an alignment has two ends only, so it branches — a new alignment from that point through the new ones is offered, its route asked as for New alignment.

  **Backspace** takes the last point back, **Escape** gives it up.
- **Edit** (tool) on a point opens its window: E, N, z or *on the ground*, tied to a structure, and the alignments it is on with its place (#) in each — ✕ takes it off one, **+ on another alignment…** puts it where it fits along that one. A shared point is one point: moved, it moves on all its alignments.
- **Delete** (tool) deletes a point: off every alignment it is on (asked first when on several); the other points keep their order. An alignment may be left without points.
- **View › Work on route** (yours only): the profile shows that route, the checks (clearances) and the structure loads keep to it, and everything else is drawn faded in the 3D view and the plan.

Files and projects of older versions are read into this form once (see [line file](line-file.md)): each alignment's points become points of their own, shared where alignments met; an alignment on several routes becomes one per route.

## Library editors

**A project keeps its libraries.** The wire library, the structure types, the insulator assemblies, the weather and load case files, the structure models (`.olsfe`) and poles (`.olsp`), the section library (`.olssec`, the profiles the structure models' members refer to: see [Section library](section-library.md)), the clearance rules (`.olsr`), galloping parameters (`.olsg`), thermal ambient cases (`.olsta`) and unit costs (`.olscost`) are stored in the project file (`.ols`), so the project alone is everything needed to open it elsewhere. Opened the first time, each kind the project does not hold yet is copied into it from where it was read (the files given, next to the project, or the default folders; structure models and poles from the structure folder, the section library from the `Sections/` folder next to the project, else the `.olssec` files next to it — never the shipped example; the others from next to the project); the line's structure checks (**fe**) use the project's section library; a library given on the command line (`--library`, `--structures`, `--insulators`; `--weather` adds its file) replaces the project's. Every save of a library page or of the weather case table goes into the project. **File › Export › Libraries…** writes them all as files into a folder (a folder per kind), and **Export…** on a page writes the file open: to share them, or to compare them with other data. A user who may not change the project (a viewer) reads the libraries from their files as before. (The model reads working copies in a temporary folder; the project is what is kept.)

The **Structures**, **Sections** and **Criteria** menus open an editor for the wire library (`.olsw`), insulator assemblies (`.olsi`), structure types (`.olss`) or weather cases (`.olswc`) — first the files the model reads: the wire library given or next to the model, `Structures/` next to it, the insulator directory, the weather case file. Choose one of them, **Browse…** for a file anywhere on the computer (in a project: copied into the project), or **New file…** to create one from a template (in a project: in the project, under the name chosen). For wires and weather cases the list on the left holds the items (**Add**, **Duplicate**, **Delete**).

**Use for the model** makes the model read the file open: the wire library or the weather case file itself; the folder of an insulator or structure type file. The model is solved again; a wire library without every cable the line uses is refused (the cables missing are named) and the model keeps its own.

A cable starts with its **model** — a list of the three cable models (non-linear; linear with creep proportional to the creep case tension; linear with a temperature increase) — and the **Bimetallic conductor** tick (a core with its own data; unticked, the core goes): choosing a model adds the fields it needs (the outer and core curves with their creep curves, or the creep temperature shift, and its tension) with example values, fields it does not use are hidden (kept in the file), and the fields a cable or its model needs cannot be removed (their 🗑 is greyed). A bimetallic cable has its own behaviour above the transition temperature, below the tick: its outer strands go into compression up to its maximum virtual compressive stress, or take none (bird cage). Sections written as `[cable.outer]` tables are edited like inline ones.

Every field is shown as written in the file, with its units (`"28.1 mm"`, `"55 GPa"`, `"-5 °C"`); numbers and lists as TOML (`23e-6`, `["clearance", "loads"]`). **add a field…** offers the fields of that kind not yet given, with an example and their meaning; 🗑 removes one. A structure type's points, wire points and strings (and version 1 attachments) are listed below its fields (add, duplicate, remove); its body and design — joints, members, materials, sections, generators, the pole, extensions, load cases — are named there and edited in the [structure application](structure-app.md) (**Edit in the structure application…**). Comments and layout of the file are kept.

### The structure screen

The **Edit** tool on a structure (or a right-click with it), and
**Strings and points…** in a structure's properties, open its **structure
screen**: for a typed structure, its type on the Structure library page
(**Pylon**, next to **Fields**); for a structure without a type, the
**Structure editor**. The screen is split: the **tables on the left**,
the **pylon in 3D on the right** — drag the divider between them (it
starts at about 45/55 and keeps its place while the program runs).

Only the basics are edited here: the **attachment points**, the
**strings** (insulator, length, weight, compression, strain) and the
**wire points with their sets**; with the structure's name, type,
extension and height adjustment in its properties and its **Placement…**
window. The body — joints, members, sections, materials, supports,
generators, the pole, extensions — and the design (load cases, analysis)
are drawn in the view for context and edited in the [structure
application](structure-app.md): **Edit in the structure application…**
at the top of the screen.

- The top line gives the **level** worked out from the file ([detail levels](structure-library.md#detail-levels)), the counts of attachment points, strings, wire points and sets, how many structures of the line use the type (they follow when it is saved) and **Edit in the structure application…**; below it, how many joints and members the body has.
- **In the view** (x to the right of the line red, y ahead green, z up blue, 0;0 at the centre, the ground grid at the level of its feet): drag to turn, right-drag to pan, the wheel to zoom, **Fit** to see it whole. A click picks an attachment point (orange) or a wire point (blue, with its set); **Shift + click** picks another. Joints and members are not picked: members with a section are steel grey, without one (sticks) sand-coloured; supported joints green.
- **Drag** an attachment point or a wire point to move it, in the plane facing you; it snaps to the **snap** grid (default 5 cm; 0: none) or onto a joint near the pointer. A point on a joint or along a member moves with the body: the screen says so (move it in the structure application).
- **+ Attachment point** adds a free one (mirrored across from the point picked, else at the top of the centre); the **I** and **V** presets hang an insulator of the length given from the point picked (or a V from the two picked) to a new wire point — its set is put by hand in **Set points** (only pylon templates number sets themselves); **Delete…** lists everything that goes with what is picked (a point: its strings) and asks.
- **Tables**, what hangs on the structure:
  - **Attachment points** — where insulators hang on the structure: a position, or the joint or member they sit on; free ones moved here (dragged, or typed); how many insulators hang from each. Moving one takes its insulators' wire points along.
  - **Insulators** — each string: what it **hangs from** (an attachment point, or another insulator's wire point: a TAK), its **wire point** (where it ends; another insulator's makes a V), its **kind** (suspension: the wire runs through its set; strain: the wire ends there), an **assembly** of the insulator library (its length, weight, wind area; a strain assembly makes it strain) or none and a **length**, its **angle** from straight down (0° hanging, 90° level) and **direction** in plan (in the project's angles), weight, wind area, the compression it may take, a description. The length and the angles **place its wire point**; a V's legs show their directions (they follow where their lengths meet). There is no "ahead" or "back": the angles alone say where it points. **+ New insulator** hangs one from the point picked (the length given) to a new wire point; **From the library…** hangs an assembly of the library there; **Save to library** (on a row) writes that insulator as an assembly of the insulator library (a V's leg as a V-string assembly); **🗑** deletes it (its wire point with it when nothing else is on it); **Insulator library…** opens the library to import, export, edit or delete assemblies.
  - **Wire points** — where an insulator ends: their position, placed by their insulator(s) (typed only for one no insulator reaches: fixed), the insulators holding each and those hanging from it, its set, a counterweight.
  - **Set points** — where a wire is strung: the **set** number (typed by you; unique on the structure), the **wire point** it is on (moved to another with this list), its **kind** from its insulator (suspension or strain; fixed without one), 🗑 to take it off; **+ Set on wire point…** puts one (the next free number) on a wire point without a set. On a structure (Apply), a set renumbered takes the sections and jumpers strung there along — two sets swapped too.

  The file's other fields are in **Fields**. Hover a column title for what it means.

**A structure without a type** opens on the same screen, the **Structure editor**, in a window of its own (drag its tab into the main window to dock it), with its points, wire points, strings and stick drawing in its own axes. Nothing changes on the line until **Apply** (one command, one undo); **Revert** goes back to the structure as it is. **Make it a type…** saves it as a structure type of the project (in its structure types folder, else a `Structures` folder next to the line), gives the structure that type — its points and strings then come from the type — and opens the type. It has no file of its own, so the structure application has nothing to open: its **Edit…** (in Properties, or **Edit in the structure application…** in the Structures table) opens this screen with **Make it a structure file and edit it…** asked — type the new type's id and press **Save, use and edit**: the type is made as with Make it a type…, and the structure application opens on its file.

**Edit… — the structure application.** **Edit…** in a structure's
properties, **Edit in the structure application…** on the structure
screen, on the Structure types page (with **Fields**) and in the
Structures table (right-click a row's ⤴) open the structure in the
[structure application](structure-app.md), a window of its own, on the
structure's file — in a project, the project's working copy of it. With
unsaved changes on the page it asks to save or discard them first (the
structure application edits the file as saved). When it is saved there,
the line application takes the file back into the project and reads the
structure libraries again, as when the Structure types page is saved:
every structure of the type follows, and the page shows the saved text
(if it has unsaved changes of its own, it says so and keeps them).

`ols-structure` is looked for in the program the `OLS_STRUCTURE_APP`
environment variable names, then next to `ols-cad` (and the folder above
it), then on the `PATH`. What goes wrong is shown in a window of its own
(the text in a box that scrolls, closed with **Close**), and written to
the log:

- **not found** — the folders it looked in and how to build it:
  `cargo build --release -p ols-structure-app` (in the OLS CAD folder; it
  lands next to `ols-cad` in `target/release`). **Start OLS CAD.command**
  builds both;
- **another build** — before it starts it, the line application asks
  `ols-structure --version` and compares the build with its own; when
  they differ it starts it anyway and warns: rebuild both, `cargo build
  --release -p ols-app -p ols-structure-app`;
- **it stops with an error** — its error output (what it wrote before it
  stopped), e.g. a file an older build cannot read.

**Edit… on a placed structure** (its properties) also hands over that
place's loads ([Started for a placed
structure](structure-app.md#started-for-a-placed-structure)): the line
application computes the loads of the line's load cases (Criteria › Load
cases) at that structure in the background and writes them beside the
structure file (`<name>.<structure>.line-values.json`); while the
structure application is open, a change of the line (once it has stayed
unchanged for a second) computes and writes them again, and the window
follows. Values typed over its load table there are saved as
`<name>.<structure>.loads.csv`; in a project the line application keeps
them in the project with that structure (library kind `loads`, per
project line) as soon as they are saved, and the status line says so.
The project's section library goes along for the members' areas. One
structure application runs per structure file: Edit… on another
structure of the same type while one is open says so.

**A structure type on its own**: `ols-cad pylon.olss`, **File › Open** (choose a `.olss`) or the start page's recent files open a structure type file without a line: its editor is the whole window — the structure screen and the file's fields (**Fields**), **Save** (⌘S), the other types of its folder in the list, **Edit in the structure application…** for its body. The insulator assemblies of its folder (and of an `Insulators` folder there) are those its strings may take. Which angle means ahead is yours for files opened alone (at the top, remembered on this computer); a project has its own (Structures › Angles around structures). Unsaved changes are asked about before another file opens. In a project, the same editor is the Structure types page, and **Strings and points…** opens a structure's type in it; what the type gives — its points, strings and wire points, with their descriptions — comes into the line with every structure of that type.

Everything changes the file as edited: **Save** writes it (the line follows), **Discard** drops the changes.

The file is checked as you type with the library's own reader; the error is shown and **Save** waits until it reads. After saving, the model reads its libraries again, resolves the structure types and solves every weather case; a page with unsaved changes shows * and does not close. 

## Controls

The 3D view is navigated with the mouse and, while the pointer is over it, the keyboard — like Minecraft in creative mode:

| Input | Action |
|---|---|
| W / S | forward / back along the ground, in the direction of view |
| A / D | left / right |
| Space / Shift | up / down |
| Ctrl (held) | four times faster |
| scroll | zoom |
| right or middle drag | pan |
| double-click | fly to the object |
| G | go to a structure: a window with every structure in a list; Enter goes (selects it, brings the 3D view within 150 m and centres the plan), Escape closes |

Two schemes, chosen in **Help › Controls › 3D** (with the speed, the look sensitivity and every key and mouse action; the 3D view shows no help text over it, only "Esc: free the mouse" in first person). **Help › Controls › Plan** and **Profile** list how those views are moved and used (more settings will come there):

- **Orbit** — left drag turns the view around the point looked at.
- **Minecraft creative** — first person, as in the game: clicking the 3D view captures the mouse (locked and hidden); moving it looks around (mouse down: look down); a crosshair marks the centre and a click selects what is under it (double-click flies to it); **Ctrl + wheel** sets the speed (the wheel alone scrolls the hotbar). **Escape** frees the mouse to use the panels (switching to another application frees it too; while a wire is strung or an alignment laid out, the first Escape gives that up and the second frees the mouse).

The speed (m/s) and, for the first-person scheme, the look sensitivity are set there too, and the list shows every key of the scheme. The scheme, speed and sensitivity are remembered for the next start; `--controls orbit` or `--controls minecraft` chooses one at start. Schemes are data (`controls.rs`: actions bound to keys and mouse buttons), so schemes familiar from other software can be added as presets, and later edited and saved.

**Edit › Snap: what can be clicked** chooses what can be clicked: structures, spans, jumpers, wire points and string tops (selecting their set), alignment points, LiDAR points (more kinds will be added); by default structures, spans and jumpers. At about the same distance, a point wins over the line it sits on and a structure over a wire. The choice is remembered.

Clicking an object in any view selects it everywhere: a structure anywhere along the lines it is drawn with (mast or stick drawing, arms), a **string** anywhere along it where it is drawn (as solved in the case shown — with the wind from both sides, each of the two; a jumper's helping strings too; its properties give where it hangs, its wire point, set, length, weight, wind area, dead end and its force in the case shown), attachment points (Snap) where the clamps are drawn, a span anywhere along its wire, a jumper anywhere along it (drawn as a bundle like its section). The properties of a jumper show its cable, section, bundle (and whether it is its own or its section's), length or sag, support string or helping strings, results in every weather case, and the force in each string holding a support clamp in the case shown ("slack" when it is), in a box of fixed height. In the 3D view the strings holding a jumper's clamps are drawn to the clamps as solved, and each clamp as a short bar along the jumper. Tabs can be dragged to rearrange the window.

Loading runs in the background. On a real 25 km line with 99.6 million LiDAR points stored in its project, the window is ready in about 8 s (release build): the whole cloud decoded (every one of its 31 classes shown, 2.1 million points), a 5-million-triangle ground surface.

## Plugins

Plugins › **Plugin manager…** lists the plugins found: those installed for you (in the application's data folder, `plugins/`) and those of the folders you added (used where they are — handy while writing one). For each: its version, kind (WebAssembly or Python), what it provides (a file-format plugin's formats), and why it cannot be used if it cannot (another interface version, permissions asked for that cannot be granted, its entry file missing — e.g. not built). The tick turns a plugin on or off (remembered). **Install from a folder…** copies a plugin into your plugins (a WebAssembly plugin's manifest and `.wasm`; a Python plugin's folder); **Remove** deletes an installed copy (after a confirmation). A plugin name found twice is used from the first place (your plugins, then the folders in order).

File-format plugins add their formats to File › Import › Into the line / Export › The line, next to the built-in ones. They run on a worker thread, sandboxed, with time and memory limits ([Writing plugins](../development/plugins.md)).

## Python console

Plugins › **Python console** opens a page with a Python interpreter in the application (Python 3.10+, the one OLS CAD was built with). Type code and press Enter (Shift+Enter: a new line; ↑ ↓: history); the value of a last expression is printed. **Run a file…** runs a script as `__main__`; **Plugin scripts** lists the Python plugins turned on. **Stop** interrupts a script (`KeyboardInterrupt`); a script running longer than the **time limit** (default 300 s) is stopped.

The `ols` module drives the open project:

| Call | |
|---|---|
| `ols.line()` | the working line, as in a line file (a dict) |
| `ols.cases()`, `ols.case()` | the weather cases, the one shown |
| `ols.results(case=None)` | the solved sections of a case: per span sag, horizontal and largest tension, mid and low points; what failed |
| `ols.selection()` | the selection, in words |
| `ols.apply(command, what=None)` | a session command (as in the operation log, e.g. `{"op": "move_structure", "id": "T2", "position": [x, y, z]}`): validated, logged, undoable; what it touches is solved again. A refused command raises |
| `ols.batch(commands, what=None)` | several commands as one (all or none, one undo) |
| `ols.undo()`, `ols.redo()` | your last command |
| `ols.status(text)` | text in the status bar |
| `ols.convert(kind, value, unit)` | unit conversion, as in the `ols` package |

```python
import ols
for s in ols.results("everyday")["sections"]:
    print(s["section"], max(p["sag"] for p in s["spans"]))
```

Each call is answered by the application at its next frame, so a script always sees the line as it is now; many edits go faster (and undo at once) in one `ols.batch`. A read-only project refuses edits.
